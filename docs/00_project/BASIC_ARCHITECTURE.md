# 選果場DX 基本設計書 v0.1

## 1. 目的

選果場で現在紙を中心に行っている以下の業務を、kintoneを中心としたデジタル運用へ移行する。

- 本日出荷情報の掲示
- 仕切り実績の記録
- 在庫管理
- 出荷時のロット入力
- 送り状番号入力
- 本日必要数量と現在庫の確認

大型モニター1台とタブレット3台を導入し、紙への記入・掲示・転記をできるだけ減らす。

基本方針は、既存の受注管理機能を活かしながら、仕切り・在庫・出荷処理を新しいkintoneアプリとして追加する。

## 2. 基本原則

各アプリの役割を明確に分ける。

- 受注管理：何を、いつ、どこへ、何ケース出す予定か
- 仕切り管理：実際に何ができたか
- 出荷処理：実際に何を出したか
- 在庫管理：実際に何が増減したか

同じ情報を複数アプリで手入力しない。

人が入力するのは、人間にしか判断できない情報を基本とし、既存データから取得可能な情報は自動取得する。

## 3. 全体構成

既存：
- 商品マスタ
- 出荷先マスタ
- 受注管理

新規：
- 仕切り管理
- 出荷処理
- 在庫管理

大型モニターとタブレットは専用DBではなく、既存・新規kintoneアプリのデータを利用するUIとして扱う。

## 4. 受注管理

既存の「受注管理（選果場出荷物）」を原則継続利用する。

1レコードは、
出荷予定日 × 出荷先 × 商品
の1明細。

受注数量の単位はケース。

受注登録は得意先ごとに、
- CSV取込
- 手入力
のいずれかで行う。

現在利用している主要機能：
- 受注登録
- 数量変更
- 追加注文
- キャンセル
- 出荷予定一覧
- 本日出荷計画
- 集計
- 送り状出力
- 出荷ロット入力
- 出荷済管理

現段階では受注管理アプリを全面再構築しない。

## 5. 本日出荷モニター

既存受注管理アプリのカスタマイズビューを利用する。

現在はkintoneのグラフ「本日出荷計画」をダウンロードし、
- 商品名
- 合計（商品名）
だけを残して使用している。

第1段階では、このExcel加工を廃止し、
商品別の本日必要ケース数を大型モニターに直接表示する。

将来的には、
- 本日必要数量
- 現在庫
- 過不足
まで表示できるようにする。

必要数量は生産指示ではなく、在庫を含めて当日の出荷を満たせるか判断するための情報として扱う。

## 6. 商品マスタ

既存商品マスタを継続利用する。

既存の規格フィールドには、
例：A長80本入
のような文字列が入っている。

在庫計算ではこの文字列を直接解析せず、構造化フィールドを追加する。

追加候補：
- 在庫管理対象
- 在庫管理単位
- 1ケース換算数量
- 等級区分
- 在庫商品区分

A・B品等は本数基準、
C品はkg基準を基本とする。

## 7. 仕切り管理

新規kintoneアプリとして作成する。

役割：
実際の選果によって完成した商品を登録する。

1レコード：
仕切日 × 生産者

1レコード内に商品明細サブテーブルを持つ。

例：
- 商品
- ケース数
- 半端本数
- kg

現在の紙運用と同様に、1生産者についてその日にできた複数商品をまとめて入力できる構造とする。

仕切り登録を在庫増加の根拠とする。

## 8. 在庫管理

新規kintoneアプリとして作成する。

現在庫を直接書き換える方式ではなく、
1レコード＝1回の在庫増減
とする。

在庫増減種別例：
- 仕切入庫
- 出荷
- 廃棄
- 破損
- 棚卸調整
- その他調整

現在庫は在庫増減履歴の累計結果として算出する。

A・B品等は本数で内部管理する。

例：
A長80本入
5ケース＋18本
= 418本

出荷3ケース
= 240本出庫

残高178本は、
画面上では2ケース＋18本として表示可能。

C品はkgで管理する。

半端本数、C品kgとも翌日へ持ち越す。

## 9. 出荷処理

新規kintoneアプリとして作成する。

役割：
実際に出荷した内容を管理する。

1レコード：
出荷日 × 出荷先

送り状番号は商品単位ではなく出荷先単位。
10個口でも送り状番号は1つ。

受注管理では複数商品が複数レコードで存在していても、
出荷処理では出荷先単位でまとめる。

通常商品は原則として受注数量＝実出荷数量。

欠品等で減らす場合は取引先へ連絡後、受注数量そのものを修正する。

## 10. AB混合・BC混合

AB混合・BC混合は取引上の商品として残す。

ただし、物理的な混合箱は廃止する。

例：
受注
AB混合 10ケース

実出荷
A品 6ケース
B品 4ケース

在庫から減らすのは実際に出したA品・B品。

受注商品と物理在庫商品を分離して扱う。

BC混合も同様。

## 11. 出荷ロット

現在の出荷ロットは6桁。

構成：
- 商品Lot 2桁
- 日付Lot 2桁
- 生産者Lot 2桁

同じ日の同じ生産者・同じ商品では同じロット番号を使用する。

日付Lotは日付＋10であり、月情報を含まない。

現段階ではトレーサビリティ高度化を優先せず、DB構造と日常管理の合理化を優先する。

## 12. タブレット運用

タブレット3台を導入する。

各端末を専用用途に固定しすぎず、
どの端末からも、
- 仕切り入力
- 出荷処理
- 在庫確認
ができる構成を基本とする。

出荷時は、現在の
紙へ記入 → 後からkintoneへ転記
を廃止し、現場で直接入力する。

入力対象：
- 出荷ロット
- 送り状番号
- 必要に応じて実出荷内訳
- 出荷完了

送り状番号はバーコード読取を第一候補とする。

出荷ロットは6桁数字スタンプのため、
初期版は手入力可能とし、
将来的にOCRを検討する。

## 13. 出荷完了時の自動処理

出荷完了時は可能な限り以下を自動処理する。

- 出荷処理アプリを完了状態へ更新
- 在庫管理へ出庫データ作成
- 受注管理を出荷済へ更新

人が同じ情報を複数回入力しない設計とする。

## 14. 在庫引当

初期版では厳密な在庫予約・引当機能は実装しない。

まずは、
- 現在庫
- 本日必要数量
- 差
を確認できる仕組みを作る。

受注登録時点での在庫予約は第2段階で検討する。

## 15. Source of Truth

- 商品情報：商品マスタ
- 出荷先情報：出荷先マスタ
- 受注・出荷予定数量：受注管理
- 仕切り実績：仕切り管理
- 実出荷内容：出荷処理
- 在庫増減履歴：在庫管理
- 現在庫：在庫管理履歴の集計結果
- 送り状番号：出荷処理

## 17. GPTとClaude Codeの役割分担

ChatGPT：
- 現状業務理解
- 要件整理
- 業務ルール決定
- 全体アーキテクチャ
- 受入条件
- 全体整合性確認

Claude Code：
- 既存資料・コード調査
- 技術詳細設計
- Plan Modeによる実装計画
- JavaScript/CSS実装
- kintone API連携
- テスト
- Git管理

業務ルール変更をClaude Code側だけで決定しない。

## 18. 標準開発フロー

1. ChatGPTで業務要件・基本設計を決定
2. Claude Code Plan Modeで技術詳細を検討
3. 既存構成との整合性・影響範囲を確認
4. 必要ならChatGPTへ戻して仕様修正
5. Claude Codeで実装
6. テスト
7. 実機確認
8. 確定仕様をドキュメントへ反映

## 19. 設計の中心思想

「予定」「完成」「実出荷」「在庫」を別の事実として管理し、
必要な画面で組み合わせて表示する。

紙の帳票をそのままkintoneへ置き換えるのではなく、
データを一度だけ正しく登録し、そのデータを複数用途で再利用できる構造を目指す。
