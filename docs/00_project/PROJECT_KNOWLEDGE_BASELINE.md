## 0. この文書の位置づけ

この文書は、選果場DXについてこれまでのヒアリング、既存kintoneアプリ調査、Claude CodeによるAs-Is調査、設計上の意思決定を、2026-10-09時点で一つに統合した基準文書である。

目的は以下の3点。

1. ChatGPT・Claude Code・ユーザーの前提を一致させる。
2. 長い会話履歴を毎回読み直さなくても、最新の業務前提と設計方針を把握できるようにする。
3. 旧方針と新方針が競合した場合に、どちらを優先するか明確にする。

### 優先順位

この文書に記載された「確定」事項は、これ以前の会話・旧設計文書にある矛盾する記述より優先する。

`BASIC_ARCHITECTURE.md`、`DECISION_LOG.md` などの正式設計文書は、このベースラインに同期している。統合受注管理V2・出荷管理V2の項目レベルの業務データモデルは `docs/20_design/ORDER_SHIPPING_V2_DATA_MODEL.md`（以下「業務データモデル」）を正式文書とする。なす仕切り・いちご製造計画・いちご受託加工の業務仕様は、`BASIC_ARCHITECTURE.md` v0.5 の各章を正式とする。

### 重要な方針変更

当初は既存の「受注管理（選果場出荷物）」を継続利用し、その周辺に新アプリを追加する想定だった。

現場ヒアリングと既存アプリ調査の結果、現在は以下へ方針変更している。

> **既存本番アプリは直接改修せず、受注・マスタ・仕切り・出荷・在庫をV2として新規構築し、完成後に切り替える。**

既存アプリは年間を通して本番業務で使用されているため、開発中の変更による業務影響を避ける。

2026-10-08に、統合受注管理V2・出荷管理V2の業務データモデルを確定した。v0.1の一部の記述（受注・出荷の粒度、送り状番号、C品kg在庫等）は上書きしている（§26）。

2026-10-09に、いちご業務、品目別数量単位、仕切りアプリの分離、産直出荷の処理場所、新旧切替（T/S）を確定した。v0.2の一部の記述（受注数量は一律ケース、いちごのケース→パック換算、産直出荷の予定出荷生成、旧受注移行案等）は上書きしている（§27）。

### 2026-10-09の統合案のうち採用しなかった点

ChatGPTの統合案（基本設計v0.5案・決定監査）のうち、以下の2点はユーザー確認により採用していない。

- **なす半端在庫の簡易残管理案**：半端在庫は v0.2 の定義（規格 × 実日付 × 日付Lot、本数、FIFO対象）を維持する（§14.3）。
- **出荷区分の「産地出荷」表記**：出荷区分の値は「選果場出荷 / 産直出荷」のまま変えない。統合案の「産地出荷」は「産直出荷」と同じ意味として扱う。

# 1. プロジェクト目的

選果場で現在行っている紙・Excel・複数kintoneアプリ・販売管理ソフトへの二重入力を整理し、kintoneを中心に以下を合理化する。

- 本日の選果・出荷必要量の大型モニター表示
- なす仕切り実績のタブレット入力
- いちごの週次製造計画・受託加工実績・SF買取仕切り
- 在庫管理（なす・いちご共通）
- 出荷処理
- 出荷Lot入力
- 送り状番号管理
- 送り状作成
- 選果場出荷と産直出荷の受注管理統合
- 将来的なFLAMとのデータ連携
- 二重入力・二重管理の削減

導入予定UI:

- 大型モニター 1台
- タブレット 3台

モニター・タブレットはDBではなくUIとして扱う。

# 3. 現行システムの重要なAs-Is

## 3.1 現在確認されている主要kintoneアプリ

- 受注管理（選果場出荷物）
- 受注管理（産直出荷物）

- なす生産者リスト（生産者マスタ）

## 3.2 受注管理（選果場出荷物）

基本粒度（現行）:

> 1レコード = 出荷予定日 × 出荷先 × 商品

数量単位:

> ケース（c/s）

主な機能:

- 受注登録
- 数量変更
- 追加注文
- キャンセル
- 出荷予定一覧
- 本日出荷計画
- 集計
- 送り状出力
- 出荷Lot入力
- 出荷済管理

受注登録方法:

- 得意先ごとにCSV取込または手入力
- 同じ得意先では概ね方式が固定
- 一部得意先からは1週間分のExcelを受領し、社内でkintone取込用に組み替えている

追加注文:

- 既存レコードの数量を変更
- 現行では「出荷」ラジオボタンの「追加」を使用することがある

問題点:

- 「未出荷 / 出荷済 / キャンセル / 追加」が同一状態フィールドに混在
- 「追加」は本来、出荷状態ではなく受注数量変更
- 現行「本日出荷計画」グラフは「追加」を除外する可能性がある

V2ではこの状態設計をそのまま引き継がない。

## 3.3 受注管理（産直出荷物）

Claude Code調査結果:

- 選果場側と同じ元アプリから派生したと見られる
- JS / CSS / プラグインなし
- 項目数は選果場側より大幅に少ない
- 共通主要項目:
  - 受注日
  - 商品名
  - 受注数量(c/s)
  - 出荷予定日
  - 納品日
  - 出荷先
  - 得意先
- 産直側固有:
  - 発注
  - 出荷確認
  - 備考

### 「発注」ラジオボタン

- アプリ作成当初は使用していた
- 現在は全く使用していない
- 現場ヒアリングでも不要と確認済み
- V2では廃止する

ただし既存アプリでは一覧・グラフの絞り込み条件に使われているため、既存設定をそのままV2へ移植しない。

### 「出荷確認」

- 産直側では現在使われていない
- 選果場側では出荷確認・出荷状態に相当する運用は使っている

V2では受注状態とは分離し、出荷処理側の業務として扱う。

## 3.4 現行2アプリの統合判断

現場ヒアリングにより、同じ商品でも出荷先や取引条件によって

- 受注管理（選果場出荷物）
- 受注管理（産直出荷物）

に分かれていることが判明した。

2アプリ間の業務構造は共通性が高く、産直固有の「発注」機能も不要となっているため、V2では統合する。

## 3.5 送り状・送り状番号（現行運用）

- 現行ではkintoneからCSVを書き出し、ヤマト・佐川・その他該当ソフトの送り状発行ソフトへインポートしている。
- ヤマトは複数個口では1個口ごとに異なる伝票番号が発行される。現在のkintoneでは最若番のみ記録している（2026-10-08 現場確認）。
- 佐川は送り状番号1件。個口数が減る場合は佐川側システムで修正・再発行している。
- その他便では伝票番号自体が存在しない場合がある。

> 確認事項：As-Is調査（docs/10_as_is/ORDER_APP_AS_IS.md §14）では、受注管理アプリに送り状番号を保持するフィールドは確認されていない。最若番の記録先は確認が必要。

# 4. V2全体アーキテクチャ

業務上のアプリ分離は確定した【確定】。マスタ・共通在庫のkintone上の物理アプリ数は技術設計で決める。

1. 商品マスタV2（共通）
2. 顧客マスタV2（共通）
3. 出荷先マスタV2（共通）
4. 生産者マスタV2（共通）
5. 統合受注管理V2（共通）
6. なす仕切り管理V2（なす専用）
7. いちご製造計画V2（いちご専用）
8. いちご受託加工管理V2（いちご専用。SF買取仕切りを内包）
9. 在庫管理V2（なす・いちご共通の業務基盤）
10. 出荷管理V2（なす・いちご共通のアプリ。レコード・画面は品目別）

外部：苺流通システム（生産者の週次エントリー、SF選果場向け振り分け。置き換えない）、FLAM（販売管理）。

既存アプリを直接改修せず、V2を別アプリとして構築する。

> v0.2までの単一の「仕切り管理V2」は、なす仕切り管理V2・いちご製造計画V2・いちご受託加工管理V2に分離した。

## 4.1 各アプリの役割

### 商品マスタV2

「何の商品か」「選果・在庫・出荷・モニター上どう扱うか」を定義する。販売商品・物理SKU・数量単位・加工後取扱区分等を持つ（§11.6）。

### 顧客マスタV2

取引先・FLAM得意先コード、標準受注受付経路、標準荷主名等を管理する。

### 出荷先マスタV2

納入先・住所・送り状関連情報、通常得意先、標準納品リード日数等を管理する。

### 生産者マスタV2

生産者情報・生産者Lot等を管理する。

### 統合受注管理V2

> 何を・いつ・どこへ・いくつ出す予定か

を管理する。全販売先、選果場出荷・産直出荷の受注明細を扱う。産直出荷の出荷済登録もここで行う。

### なす仕切り管理V2

> なすの選果・仕切りで、生産者ごとに何ができたか

を管理する（§13）。

### いちご製造計画V2

> いちごを週にどれだけ作るか、生産者別にどれだけ買い取る目標か

を管理する（§15）。

### いちご受託加工管理V2

> いちごを生産者ごとにどれだけ加工し、そのうち何をSFが買い取ったか

を管理する（§16）。

### 出荷管理V2

> 選果場出荷を実際にどう出荷したか

を管理する。送り状、出荷Lot、出荷完了などはここに置く。産直出荷は扱わない。

### 在庫管理V2

> SF所有在庫がなぜ増減したか

を管理する。

## 4.2 V2全体原則【確定】

### 入力の原則

- 同じ情報を複数アプリへ人が二重入力しない。
- 通常値はマスタ・ルールから自動設定し、対象レコードへスナップショット保存する。
- 例外の場合だけ人が修正する。
- マスタとはIDで正式に紐付け、名称は登録時点のスナップショットとして保存する。

### 業務を止めない原則

- システム上の不整合を理由に現場業務を止めない。
- 在庫不足、Lot未入力、送り状番号未入力等は原則として警告し、例外理由を記録すれば続行可能とする。
- 重複ID・データ破壊・識別不能につながる操作のみ強く制限する。

### 数量単位

- なすはケース、いちごはパック（P）。受注・製造・完成・買取・在庫・出荷のすべてに適用する。
- 数量単位は商品ごとの属性とする。
- いちごの230g換算パックは、生産者間の配分と公平性の比較にだけ使う。

## 4.3 エンティティの関係【確定】

- 受注明細（選果場出荷）n : 1 出荷（1物理発送）。産直出荷の受注明細は出荷に紐付かない
- 受注明細 1 : n 受注変更履歴
- 受注明細 1 : n 実出荷明細（通常1:1。AB/BC混合で複数）
- 実出荷明細 1 : n 出荷Lot使用
- 出荷 1 : 0..n 出荷後例外
- 出荷完了 → 在庫管理V2の出荷イベント（実出荷明細基準。在庫管理対象の物理SKUのみ）
- なす仕切り確定 → 在庫管理V2の入庫イベント
- いちご完成実績（SF買取SKU）→ 買取仕切り候補 → 買取確定 → 在庫管理V2の入庫イベント

# 5. 統合受注管理V2

詳細は業務データモデル §3。

## 5.1 レコード粒度【確定】

> 1レコード = 1受注明細

- 同一の **得意先 × 出荷先 × 出荷予定日 × 納品日 × 商品 × 出荷区分** であれば、追加注文が来ても別レコードを作らず数量を集約する。
- 発送元が異なる場合等、同一物理発送にならない場合は別明細とする。
- この組み合わせ自体を一意キーにしない。別途、不変の `受注明細ID` を自動採番する。

> v0.1の「1レコード = 出荷予定日 × 出荷先 × 商品」を置き換える。

## 5.2 受注数量【確定】

- 数量単位は商品ごとの属性とする。**なすはケース（c/s）、いちごはパック（P）**。
- v0.2の「通常受注はケース（c/s）単位」は置き換えた。
- サンプル等、数量単位が特殊な業務は、初期版の通常受注フローと区別する。必要なら後工程で検討する（候補）。

## 5.3 主なフィールド【確定】

- 受注明細ID
- 受注日
- 出荷先ID / 出荷先名
- 得意先ID / 得意先名
- 出荷予定日
- 納品日
- 商品ID / 商品名
- 受注数量
- 数量単位（商品マスタから自動）
- 出荷区分
- 発送元ID / 発送元名
- 初回受注受付経路
- 登録方法
- 受注状態
- 出荷状態
- 出荷ID（選果場出荷のみ）
- 元受注明細ID
- 受注備考

名称等はマスタIDで正式紐付けし、名称は受注時点のスナップショットとして保存する。

kintoneのフィールド型・フィールドコードは技術設計で決める。

## 5.4 自動設定ルール【確定】

| 項目 | ルール |
|---|---|
| 受注日 | kintoneへの登録日ではなく、実際に得意先から注文を受けた日。登録日時はkintone標準の作成日時等で別管理 |
| 得意先 | 出荷先を選ぶと出荷先マスタの「通常得意先」を自動設定。受注明細へ正式保存し、例外時は変更可能 |
| 納品日 | 出荷先マスタの「標準納品リード日数」で出荷予定日から自動計算。例外時のみ修正。複雑な土日祝配送カレンダーは初期版では不要 |
| 出荷区分 | §5.5 |
| 発送元 | 選果場出荷 → 選果場。産直出荷 → 商品等から標準発送生産者を自動設定。独立フィールドとして保持（同じ産直商品を複数生産者が発送する通常運用は現状ない） |
| 初回受注受付経路 | FAX / 電話 / メール / LINE / WEB / その他。得意先マスタの標準値から自動設定し、例外のみ修正 |
| 登録方法 | 手入力 / CSV取込 / 将来自動連携 等。システムが自動記録。受付経路とは別概念 |

## 5.5 出荷区分【確定】

受注明細ごとに明示的な `出荷区分` を持つ。

値:

- 選果場出荷
- 産直出荷

### 重要

`出荷区分` は出荷先ごとに固定ではない。同じ出荷先でも注文によって選果場出荷と産直出荷が変わる可能性がある。

- 出荷先マスタの固定属性だけでは管理しない
- 受注明細ごとの属性として保存する
- 商品名や商品先頭番号から推定しない

### 標準値

- 標準値は **出荷先 × 商品** の組み合わせから自動設定する。
- 未登録の組み合わせでは担当者が選択し、必要なら営業へ確認する。
- その決定を今後の標準値として登録可能とする。
- 今回だけ例外変更した場合は標準値を自動変更しない。
- 組み合わせ依存ルールのため、商品マスタ単体に持たせない。管理UIは未確定。

## 5.6 状態管理【確定】

旧アプリの状態設計をそのまま引き継がない。

| 状態 | 値 |
|---|---|
| 受注状態 | 有効 / キャンセル |
| 出荷状態 | 未出荷 / 出荷済 |

値はこれのみとする。

出荷済の更新:

- 選果場出荷：出荷管理V2の出荷完了により自動で更新する。
- 産直出荷：初期版では、事務所等の担当者が統合受注管理V2で手動で出荷済を登録する（§6.5）。

### 追加注文

「追加」は状態にしない。

例: 4ケース → 6ケース であれば、受注数量を6へ変更し、受注変更履歴に残す（§5.8）。

## 5.7 キャンセル・削除【確定】

- 正式受注は削除しない。
- 全量キャンセルでも元の受注数量を保持し、`受注状態 = キャンセル` とする。数量を0へ書き換えない。
- 削除を許可するのは以下等のみ。
  - 二重登録
  - テスト登録
  - 明らかな誤登録
  - 実際には受注が存在しなかったデータ

## 5.8 受注変更履歴【確定】

数量変更だけでなく、数量・出荷予定日・納品日・商品・出荷先・得意先・出荷区分・発送元・キャンセル等の重要変更を「受注変更履歴」として残す。

扱う項目:

- 変更日時
- 変更者
- 変更対象
- 変更前
- 変更後
- 数量の場合の増減量
- 変更理由
- 受付経路
- 外部注文番号・発注番号
- 備考

変更前後、変更日時、変更者等は極力自動記録する。人に入力させるのは原則として変更理由のみ。

具体的な実装方式は未確定（技術設計）。

> v0.1の「変更履歴はkintoneの履歴等で追跡できる」を置き換える。kintone標準の変更履歴だけに依存しない。

## 5.9 重複受注【確定】

同一条件の有効受注明細が存在する場合、自動新規登録・自動加算しない。

担当者に以下を提示する。

- 追加発注として加算
- 既存受注を開く
- 中止

追加を選んだ場合だけ既存数量へ加算し、変更履歴を残す。

## 5.10 Excel / CSV【確定・一部要調査】

初期版では以下とする。

- 週次Excel = 初回受注の一括登録
- その後の追加・減数 = LINE・電話等による既存受注変更
- 同一取込データの二重取込を警告・防止
- 修正版Excelは例外的な訂正

修正版Excelの高度な自動差分反映は初期版必須ではない。

取込UIの方向（得意先指定 → ファイル選択 → 事前プレビュー → 確定、原本保存・取込履歴・重複検知・行単位エラー）は BASIC_ARCHITECTURE.md §5.9。実ファイルの形式は現物で確定する。

同じ受注を、苺流通システム経由と他ルートの入力で二重登録・二重計上しない。苺流通システム連携の実装方式は未確定。

## 5.11 欠品追送【確定】

- 欠品時は得意先へ連絡し、元受注数量を当日出荷可能数量へ修正する。
- 不足分の追送を顧客が希望した場合は、翌日以降の別受注明細として登録する。
- 追送明細には `元受注明細ID` を保持する。

## 5.12 産直「発注」機能【確定】

廃止確定。

- 未発注
- 発注済
- キャンセル（未手配）
- キャンセル（手配済）

という旧概念はV2に引き継がない。キャンセルは受注状態として管理する。

## 5.13 備考

共通の `受注備考` を持つ【確定】。

# 6. 受注管理と出荷管理の分離・予定出荷

## 6.1 分離理由【確定】

受注と出荷ではレコード粒度と業務責任が異なる。

- 統合受注管理V2：何を出す予定か（1受注明細）
- 出荷管理V2：選果場出荷を実際にどう出荷したか（1物理発送）

送り状番号・個口数・荷主名・物流業者は物理発送単位の情報であるため、受注明細に重複保持せず出荷管理V2に置く。

## 6.2 二重入力はさせない【確定】

アプリは分離するが、受注情報を人が出荷管理へ再入力する設計にはしない。

出荷管理で人が入力するものは、実出荷時にしか分からない情報を中心とする。

- 代表送り状番号
- 出荷Lot（使用数量はFIFOで自動配分）
- 特殊梱包時の確定個口数
- 実出荷内容に差異がある場合の補正（AB/BC分解を含む）
- 出荷完了

## 6.3 予定出荷の自動生成【確定】

- **選果場出荷**の受注登録時に、出荷管理V2の予定出荷レコードを自動生成する。
- 既存未出荷レコードが存在すれば自動的にそこへ紐付ける。
- 通常の自動グルーピング条件（業務上の候補。最終条件は技術設計で検証）:

> 出荷日 × 納品日 × 出荷先 × 得意先 × 発送元 × 品目

- 品目を含める理由は、なす・いちごを混載しないため（§6.4）。
- 得意先を含める理由は、同一出荷先でも帳合先が異なる荷物を同一送り状へまとめないため。
- この組み合わせを一意キーにしない。正式識別子は `出荷ID`。
- 特殊事情では同条件でも複数物理発送を許容する。
- 未出荷中の受注変更は予定出荷へ自動追従する。

> v0.2の「受注登録時に予定出荷を自動生成（出荷区分を問わない）」「グルーピング条件に品目なし」を置き換える。

## 6.4 なす・いちごの混載禁止【確定】

- なす・いちごは、同じ便・同じ送り状で混載しない。
- 1つの出荷レコードにも混在させない。同じ出荷日・同じ出荷先でも、品目ごとに別の物理発送とする。
- 出荷管理V2はなす・いちご共通のアプリとし、出荷レコードと入力画面は品目別とする。

## 6.5 産直出荷【確定】

- 産直出荷も統合受注管理V2で受注管理する。
- 出荷管理V2の予定出荷・実出荷レコードを生成しない。在庫イベントも作らない。
- 初期版では、事務所等の担当者が統合受注管理V2で手動で出荷済を登録する。外部連携の自動化は初期版では必須としない。

## 6.6 出荷完了と受注明細【確定】

選果場出荷は、出荷管理V2の出荷完了により、関連する受注明細を自動で出荷済に更新する。受注管理側で別途手動で「出荷済」を二重入力しない。

# 7. 出荷管理V2

詳細は業務データモデル §5〜§8。

## 7.1 レコード粒度・状態【確定】

> 1レコード = 1物理発送

- 対象は選果場出荷だけ。1レコードは1品目だけを含む（§6.4）。
- 受注登録時点から「予定出荷の器」として存在し、出荷時に実績情報を加え、出荷完了によって実績として確定する。
- 状態は 未出荷 / 出荷完了 のみ。中間状態は持たない。

> v0.1の「基本粒度 = 出荷日 × 出荷先」を置き換える。

## 7.2 主なヘッダ情報【確定】

- 出荷ID
- 品目
- 出荷日
- 納品日
- 出荷先ID / 出荷先名
- 得意先ID / 得意先名
- 発送元ID / 発送元名
- 荷主名
- 物流業者
- 自動計算個口数
- 確定個口数
- 代表送り状番号
- 送り状CSV出力日時 / 出力者
- 送り状番号登録日時 / 登録者
- 出荷状態
- 出荷完了日時
- 出荷完了者
- 出荷備考
- 例外完了情報
- 出荷後例外情報

## 7.3 荷主名・物流業者【確定】

- 荷主名：得意先ごとに標準値を持ち自動設定。一部得意先では得意先名にする必要がある。例外時のみ出荷管理側で変更可能。
- 物流業者：発送元 × 出荷先 でほぼ決まる。標準値を自動設定し、荷量偏り等の例外時のみ変更する。同一日の同一発送をヤマト・佐川に分割する通常運用はない。

## 7.4 個口数【確定】

- 商品によって何ケースで1個口かが異なる。異なる商品でも同じ梱包グループなら一緒に縛る場合がある。
- 商品マスタV2等に「個口計算グループ」「標準ケース数/個口」を持たせる。
  - 例：A長1cs ＋ B品1cs、同じ「なす通常箱」グループ（2cs/個口）→ 1個口
- 出荷管理V2に「自動計算個口数」「確定個口数」を持つ。通常は自動値、特殊梱包時のみ手修正。

## 7.5 実出荷明細【確定】

通常は受注明細から自動生成する。

> 通常：1受注明細 → 1実出荷明細

受注内容と同じなら現場は触らない。

扱う項目:

- 実出荷明細ID
- 元受注明細ID
- 受注商品ID / 名称
- 実出荷商品ID / 名称
- 実出荷数量（なすはケース、いちごはパック）
- 差異区分
- 差異理由
- 明細備考

在庫を減らすのは、実出荷の物理SKUである（在庫管理対象のSKUのみ。§14.1）。

## 7.6 受注数量と実出荷数量【確定】

通常:

> 受注数量 = 実出荷数量

欠品が発生する場合は取引先へ連絡し、受注数量そのものを修正する（追送は別受注明細、§5.11）。

出荷処理側で独自に「受注10、実出荷8」のような減数を通常運用にしない。

## 7.7 出荷完了【確定】

出荷完了は、原則トラック出発後（なすはLot入力後）に実行する。

完了操作により以下を自動実行する。

1. 出荷管理V2を出荷完了
2. 実出荷明細を基準に在庫管理V2へ出荷イベントを作成（商品マスタ等でSF所有在庫の管理対象と判定された物理SKUのみ）
3. 関連する統合受注管理V2を出荷済へ更新

在庫管理対象外の物理SKUだけの選果場出荷でも、1と3は通常どおり行う。

完了日時・完了者は自動記録する。

いちごは、生産者別・パック詰め日別のSF在庫をFIFOで使う。

## 7.8 例外完了【確定】

以下のような場合も原則として業務を止めない。

- システム在庫不足
- Lot未入力
- 代表送り状番号未入力
- 個口数未確定
- 混合商品の数量不一致
- その他情報不足

- 警告内容はシステムが自動記録する。
- 人は例外理由を選択し、必要時のみ備考を入力する。
- 例外完了日時・実行者を自動記録する。
- 一時的に理論在庫がマイナスになっても、実際に出荷した事実の記録を優先する。

## 7.9 出荷後の記録訂正と出荷後例外【確定】

記録誤りの訂正と、実際の出荷後の事象を区別する。

記録誤りの訂正:

- 出荷完了後の記録誤りは、変更履歴・変更理由を残し、在庫との差分調整で整合させて訂正できる。
- 無履歴の直接上書き・二重出庫は禁止する。

出荷後例外（実際の事象）:

- 顧客がキャンセル連絡を忘れており出荷後に停止依頼が来るケース等は、元の受注・出荷を取消すのではなく出荷後例外として記録する。
- 例外種別例：配送停止 / 営業所引取 / 返送 / 別販売 / 廃棄 / その他
- 返品・再出荷も、初期版では出荷後例外として記録する。商品が戻り再販売可能となれば在庫管理V2で在庫調整する。
- 専用の返品・再出荷機能、専用アプリは作らず、初期版では出荷管理V2の付帯情報で十分。

> v0.2の「出荷完了後の重要項目は原則修正不可」を置き換える。

## 7.10 送り状CSV【方向】

- V2では送り状CSVの出力元を出荷管理V2とする方向。
- 物流業者ごとのCSVレイアウトは後の技術設計・現物確認で確定する。

# 8. 出荷Lot

## 8.1 現行仕様

以下は**なすの現行運用**である。いちごに一律に同じ番号体系を要求しない（§8.4）。

出荷Lotは6桁。

構成:

1. 商品Lot 2桁
2. 日付Lot 2桁
3. 生産者Lot 2桁

例:

`商品Lot + 日付Lot + 生産者Lot`

## 8.2 日付Lot

日付 + 10。

月は含まれないため、翌月同日で同じ番号になることがある。

## 8.3 特徴

- 通し番号ではない
- 同日・同生産者・同商品は同じLot
- 「こづち」機械でアナログ6桁スタンプを貼付
- 1受注明細が複数Lotにまたがる可能性あり
- 現在も実運用で使用している
- 入力はトラック出発後に行う運用
- 選別時、半端の入った箱にはLot番号を2枚付ける場合がある

## 8.4 V2での扱い【確定】

- 商品ごとに「出荷Lot管理対象 / 対象外」を持つ。Lot管理対象商品のみLot入力を通常要求する。
- 1実出荷明細に複数Lotを許容する。
- 商品Lotを一意キーにしない。
- Lot別使用数量はデータとして持つが、現場には原則入力させない。
  - 在庫の古い日付からFIFOでシステムが自動配分（提案）し、実態と異なる場合だけ修正する。
  - なすは実日付、いちごはパック詰め日をFIFOの基準とする。
- §8.1の6桁構成はなすの現行運用。いちごの出荷Lotの番号体系・入力方式は要調査。
- Lot入力UI・FIFO自動配分UIは未確定（技術設計）。

## 8.5 優先度

トレーサビリティの高度化は当面の最優先課題ではない。

まずはDB構造と管理業務の合理化を優先する。

将来的にタブレットカメラによる数字OCRも検討可能。

# 9. 送り状番号【確定】

- 送り状番号は商品明細単位ではなく、物理発送単位。受注明細ではなく出荷管理V2に置く。
- 物流業者ごとの実態（§3.5）に基づき、正式表現を以下とする。

> **V2では1物理発送につき代表送り状番号を最大1件保持する。**

| 物流業者 | V2での扱い |
|---|---|
| ヤマト | 最若番を代表送り状番号として1件保存。全番号管理はしない。個口数が減った場合は減った分の伝票を廃棄する |
| 佐川 | 1件記録する。個口数が減る場合も佐川側システムへ修正を入れて再発行する |
| その他便 | 伝票番号が存在しない場合があり、空欄可 |

- ヤマト・佐川では通常入力するが、業務を止めない原則により、緊急時は警告＋理由記録で出荷完了可能とする。
- 送り状バーコードは存在するため、将来的にタブレットカメラで読み取る方向を検討する【方向】。

> v0.1の「出荷先単位」「同一出荷先で10個口でも送り状番号は1つ」は、現場再確認により訂正した。

# 10. 選果場大型モニター

## 10.1 最重要要件

大型モニターに表示するのは受注明細そのものではない。

表示したいのは:

> **本日、選果場でどの規格がどれだけ必要か**

という規格別必要数量。

品目によって必要数量の意味が異なる。

- なす：規格別の必要ケース数は生産指示ではない。出来高は生産者が持ち込んだ茄子の品質・量で決まるため、在庫を含めて当日の出荷を満たせるか判断するための情報。
- いちご：販売先別SKUの必要パック数は、選果場の製造目標（§15）。各生産者への割当は選果場が品質等を見て判断する。

## 10.2 対象品目と画面【確定】

当面:

- なす
- いちご

なすといちごは完全に別画面とする。Source of Truthはどちらも統合受注管理V2（いちごは苺流通システムの選果場振り分け分を含む）。

### なす

- 規格別の必要ケース数。
- 入り数違いの物理SKUでも、同じ `モニター集計規格` にまとめる（例：A長80本入・A長70本入 → A長）。
- AB/BCは初期版ではA/B等へ事前配分せず、`AB混合 ○cs` のまま混合規格名でケース表示する。

### いちご

- 販売先別・規格別の必要パック数。
- 統合受注管理V2の受注数量はパックで持つ。ケース→パック換算はしない。
- 選果場製造目標は、苺流通システムのアライド向けSF選果場振り分け分＋その他販売先の選果場出荷分とする。同じ注文を二度加算しない（§15）。

> v0.2の「いちごは受注数量（ケース）を1ケース当たりパック数で換算」を置き換える。

### 利用開始

- V2モニターはシステム移行日Tから使用する。T前は現行の紙運用を続ける。
- 旧受注はV2へ移さないため、V2モニターに含まれない。T〜旧受注完了の間の扱いは、本番切替までに解決すべき運用上の確認事項（§18.3）。
- 正式在庫管理開始日S前はV2在庫が暫定値のため、現在庫・過不足は確定値として表示しない、または暫定と明示する（技術設計）。

## 10.3 「選果場出荷」と「モニター対象」は別概念【確定】

重要:

> 選果場出荷であっても、選果場で選果・規格調整を行わない商品がある。

例:

- 産地から持ち込まれたものを、そのまま出荷する商品

これらは「選果場出荷」ではあるが、規格別必要量を表示するモニター集計の対象には含めない。

したがって:

`出荷区分 = 選果場出荷`

だけではモニター対象を判定しない。

## 10.4 モニター対象判定【方向】

商品マスタ等に明示的な属性を持たせる。属性名は候補。

- モニター集計対象
- 品目
- モニター集計規格
- モニター集計単位

## 10.5 モニター用DBの考え方【確定】

モニター情報を人が別途手入力するSource of Truthにはしない。

基本:

> 統合受注管理V2の有効受注（いちごは苺流通システムの選果場振り分け分を含む）
> → 商品マスタの集計属性で対象判定
> → 規格別必要数量へ集計
> → モニター表示

派生データとして扱う。必要量・目標の計算根拠と更新時刻を追跡可能にする【方向】。

## 10.6 産直出荷

産直出荷は選果場モニター対象外。

- 入り数は時期により2段階
- 切替時期は毎年おおむね同じだが微妙に前後する
- 同じ出荷日でも取引先によって旧入り数 / 新入り数が混在し得る

ことが確認された。

したがってV2では、

> **ケース入り数が異なるものは別物理SKUとして商品マスタV2へ登録する。**

例:

- A長80本入
- A長70本入

受注・出荷・完成品在庫も別SKUで管理する。一方、モニター集計規格は両方とも `A長` にできる。

## 11.5 AB混合・BC混合【確定】

- AB混合・BC混合は販売商品として今後も販売可能。廃止商品ではない。
- 選果場の確定方針として、物理的な混合箱は作らない。
- 受注例：AB混合 10cs → 実出荷例：A品 6cs ＋ B品 4cs
- 配分比率は固定しない。その日の出来高・在庫状況で決定する。
- 商品マスタ側で「許容実出荷商品」を定義する。
  - AB混合 → A品・B品のみ許容
  - BC混合 → B品・C品のみ許容
- 混合商品の分解は正常運用なので差異理由を人に入力させない。
- 在庫を減らすのは受注商品ではなく実出荷商品。
- モニター初期版ではAB/BCを事前配分せず `AB混合 ○cs` のまま表示する（§10.2）。

> v0.1の「取引商品・受注商品としてAB混合 / BC混合が残る可能性はある」を、「販売商品として継続」に確定した。

## 11.6 商品マスタV2へ引き継ぐ属性

- 不変の商品IDを正式キーとする。商品名・先頭番号・商品Lotは一意キーにしない。

### 商品マスタ詳細設計へ送る属性【方向】

属性名は候補、型・値は詳細設計で確定する。

- 商品ID

# 13. なす仕切り管理V2

## 13.1 レコード粒度と入力【確定】

> 1レコード = 生産者の選果・仕切り作業1回

- 同じ生産者が同日に複数回作業すれば、別の作業として記録できる。
- 扱う項目：作業日、生産者、作業順序（または前作業の参照）、SKU別完成ケース数、A/B規格別の半端、C品kg等。
- A/Bの仕切り数量は**本数**、C品の仕切り数量は**kg**。
- 完成品在庫は物理SKU別のケース（例：C品10kg/ケース）。換算値はSKUの属性に従う。

> v0.2の「1レコード = 仕切日 × 生産者（基本案）」「C品の仕切り入力単位は未確定」を置き換える。

## 13.2 仕切り数量の計算【確定】

A/Bの当該作業分（同じ引継ぎ区分ごと）:

> 当該作業分 ＝ 完成ケースの換算本数 ＋ 終了時半端本数 − 開始時引継ぎ半端本数

- 同じ半端が次の生産者の箱に入ることがあるため、生産者別仕切りの二重計上を避ける。
- 開始時の半端は、直前の作業の規格別終了半端から自動で引き継ぐ。日をまたぐ半端も持ち越す。
- 仕切り計算に使う作業開始時・終了時の半端は、正確に記録する。

## 13.3 確定と在庫【確定】

- 仕切り確定時に、完成品SKUをSF在庫へ入庫する。
- 確定済み実績の訂正は差分調整で行い、重複入庫しない。
- 半端在庫の管理軸は §14.3（規格 × 実日付 × 日付Lot、FIFO）。作業単位の半端引継ぎとの両立方法は技術設計。

## 13.4 実務確認（要調査）

- 持込コンテナ数等の入力場所・粒度
- 同日複数作業の実際の運用、半端引継ぎの手順、既存の仕切り用紙

生産者は既存の「なす生産者リスト」を調査し、V2生産者マスタへ整理する。

# 14. 在庫管理V2

## 14.1 基本方針【確定】

- なす・いちご共通の在庫管理基盤とする。管理軸・数量単位は品目ごとに変える。
- 初期版では運用負荷を最小化する。
- 在庫予約では数量を減らさない。選果場出荷の出荷完了を実在庫の減少イベントとする。
- 在庫減算は、商品マスタ等でSF所有在庫の管理対象（選果場在庫管理対象）と判定された実出荷物理SKUに限る。対象外の物理SKUでも、出荷完了と受注の出荷済更新は通常どおり行う。選果場出荷であっても、在庫管理対象とは限らない。
- 一時的に理論在庫がマイナスになっても、実際に出荷した事実の記録を優先する。
- 産直出荷は選果場在庫の対象外。
- kintone上の物理アプリ数は技術設計で決める。

在庫イベントは以下の3つに簡略化する。

1. 入庫（なす仕切り確定 / いちご買取確定）
2. 出荷（選果場出荷の出荷完了時に、実出荷明細を基準に自動作成）
3. 在庫調整

正式在庫管理開始日Sの初期残高確定も、履歴として残す（§14.7）。

> v0.2の「仕切入庫」は「入庫（なす仕切り確定 / いちご買取確定）」に置き換えた。

## 14.2 在庫調整で扱うもの

- 80本入り → 3本パック等への作り替え
- 詰め替え（80本入 → 70本入 等）
- 検品ロス
- 傷み・廃棄
- 数量訂正
- 出荷後例外で戻り、再販売可能となった商品
- その他差異

初期版では厳密な製造変換履歴を持たない。

## 14.3 在庫管理軸と単位【確定】

| 在庫区分 | 管理軸 | 数量単位 |
|---|---|---|
| なす完成品在庫 | 物理SKU × 実日付 × 日付Lot | ケース |
| なす半端在庫 | 規格 × 実日付 × 日付Lot | 本数 |
| いちごSF買取品 | 生産者 × 物理SKU × パック詰め日 | パック |
| いちご生産者返却品 | SF所有在庫の対象外 | — |
| 産直出荷品 | 選果場在庫の対象外 | — |

なす:

- 半端もFIFO対象である。規格だけで集約して日付を失わないこと（2026-10-09 ユーザー確認により維持）。
- 生産者番号は在庫管理軸にしない。
- 半端は翌日へ持ち越す。
- C品も在庫管理はケース単位でよい。

例：80本入1cs（実日付D・日付Lot L）を70本入へ詰め替え

- 80本入SKU（D・L）−1cs
- 70本入SKU（D・L）＋1cs
- 半端（A長・D・L）＋10本

> v0.1の「A/B品は内部本数ベース（例：80本入り5ケース+18本 = 418本）」「C品はkg管理、C品kg在庫は翌日へ持ち越す」を置き換える。

## 14.4 なす在庫Lot【確定】

- 在庫段階では生産者番号は管理不要。必要なのは「実日付・日付Lot + 物理SKU（完成品）/ 規格（半端）」。
- 現場表示は「商品Lot2桁 + 日付Lot2桁 = 4桁」を使用可能。ただし4桁自体をDB一意キーにしない。
- 日付Lotは月を含まず翌月同日に重複するため、日付Lotだけでなく実際の暦日（実日付）を管理軸に含める（§14.3）。
- 同じ管理軸なら、生産者が異なっても在庫は合算する。

## 14.5 詰め替え・半端とLot【確定】

- 初期版では厳密な製造変換履歴を作らず「在庫調整」で扱う。
- 80→70本等の詰め替えで半端を組み合わせて箱を作る場合は古い日付を採用する。
- 現物ラベルの生産者番号は `00` とする（生産者番号は在庫管理軸ではない）。
- FIFO上の年齢をリセットしない。システム内部でも、詰め替え後の在庫は元在庫のうち最も古い実日付・日付Lotを引き継ぐ。

## 14.6 いちご在庫【確定】

- SF買取確定品だけをSF在庫とする。生産者返却SKUはSF在庫に入れない。
- パック詰め日をFIFOの基準とし、同じ生産者・物理SKUの在庫の中で古い順に出庫する。
- 買取日とパック詰め日は別データとして持つ。
- SF買取品は、通常の販売先を想定して買い取った場合でも、販売先別の在庫所有・独占引当にはしない。割当先は必要に応じて変更できる。

> v0.2の「いちごの在庫管理をどこまで対象とするかは未確定」を置き換える。

## 14.7 暫定期間と正式在庫管理開始日S【確定】

- システム移行日T〜正式在庫管理開始日S前のV2在庫は暫定値とする。不足警告・FIFOの結果・モニターの差分を実在庫の真実として扱わない。
- Sでの棚卸・補正は、商品別の総数量ではなく、**確定済みの在庫管理軸ごとに正しい残高を登録する**ことを原則とする。
  - なす完成品：物理SKU × 実日付 × 日付Lot
  - なす半端：規格 × 実日付 × 日付Lot（FIFO）
  - いちごSF買取品：生産者 × 物理SKU × パック詰め日
- 初期残高・差分調整は履歴付きで登録する。過去の入出庫は復元しない。
- S以降のV2在庫を正式な管理数値とする（§18）。

## 14.8 3本パック

- 1パック = 3本
- 1ケース = 20パック

実際には選果時に最終形で作ることが多い。

在庫が多い場合、既存商品を出荷日に3本パック等へ詰め替える場合がある。

初期版では厳密な変換トレースはせず、在庫調整で扱う。

# 15. いちご製造計画V2【確定】

v0.2では欠番だった節番号を、v0.3でいちご製造計画V2に使用した（§20以降の番号は維持）。

## 15.1 前提

- いちごは生産者からの受託選果・パック詰めである。生産者間の現物は混ぜない。半端は同じ生産者の翌日へ繰り越す。
- 苺流通システムは、生産者の週次エントリーとSF選果場振り分けを担う。苺流通システムの注文すべてが選果場向けではない。

## 15.2 週次の製造必要量

- 選果場の必要量は、苺流通システムのアライド向けSF選果場振り分け分と、その他販売先の選果場出荷分を**合算**して決める。同じ注文を二重に加算しない。
- 選果場全体では、販売先別SKUとその必要パック数を管理する。
- 週途中の受注・振り分け変更を反映し、週次製造目標を再計算できるようにする。確定済みの加工・買取実績は変えない。目標の変更履歴を残す。
- 計画は入出庫しない。

## 15.3 生産者別の公平なSF買取目標

- 生産者別の目標は、販売先ごとには配分せず、全販売先を合算したSF買取総量を対象とする。
- 配分比率は、苺流通システムのSF選果場向け振り分け数量（230g換算P）の比率で計算する。他の振り分け先向けの数量は分母に含めない。
- 230g換算P ＝ 実パック数 × 商品マスタの公称内容重量(g) ÷ 230g。完成パックの現物重量は毎回計測しない。
- 生産者別目標は週単位の目安であり、上限ではない。日次実績を積み上げて評価する。
- 各生産者にどの販売先別SKUをどれだけ作るかは、選果場が品質・時期・販売先仕様を見て判断する。システムは生産者と販売先の組み合わせを固定しない。

## 15.4 要調査

- 苺流通システムの振り分けデータの項目、変更時の扱い、受注との同一性の判定（現物データが必要）
- 230g換算の小数桁・表示丸め（技術設計）

# 16. いちご受託加工管理V2・SF買取仕切り【確定】

v0.2では欠番だった節番号を、v0.3でいちご受託加工管理V2に使用した（§20以降の番号は維持）。

- 加工実績の基本粒度は「加工日 × 生産者」。同じ生産者を同日に複数回処理する場合のUIと識別は要調査。
- 1作業に複数の完成SKU・数量行を持つ。完成数量は原則パック。特殊単位のSKUはマスタに従う。

- 確定済みの加工・買取数量を訂正するときは、履歴と差分在庫イベントで調整し、二重入庫を防ぐ。

# 17. FLAMとの関係

## 17.1 現状

販売管理ソフト:

> FLAM

現状の入力順:

1. kintoneへ先に受注入力
2. FLAMへ再入力

そのため二重入力・二重管理が発生している。

## 17.2 FLAMの役割

現状、集計・販売管理はFLAM側で行っており、kintone受注アプリの集計機能は主要目的ではない。

## 17.3 将来方向

V2では以下を検討する。

> 統合受注管理V2
> → FLAM固定取込フォーマットに合わせたCSV生成
> → FLAMへアップロード

ユーザー契約は最も安いプラン。

CSVレイアウト自由設定が使えない可能性があるため、FLAM側を自由化するのではなく、kintone側からFLAMの固定フォーマットに合わせる方向を第一候補とする。

ただし実装前に、実際の契約プラン・FLAM画面・取込仕様を再確認する。

変換の方向【方向】:

- FLAM出力は「販売商品 × 得意先 × 納品日」を基本の変換軸とし、必要な場合だけ追加属性を使う。
- なすの4価格期は、固定日付でハードコードせず、管理できる有効期間ルールとする。

業務を止めない【確定】:

- FLAM商品コードのマッピングがない・複数候補のときは、FLAM出力だけを止める。出荷業務は止めない。

受託加工【確定】:

- いちごの受託加工数量は、SF買取対象と生産者返却対象の全完成数量から作る。選果場DX初期版は加工料金・金額を計算しない。

## 17.4 FLAMとの商品関係【確定】

なすについて、

- kintone物理SKU：入り数差等を表現
- FLAM商品：価格変更により4段階

という別概念である。FLAMの4段階切替も毎年おおむね同時期だが、実際の日付は前後する。

したがって、

> **kintone商品1件 = FLAM商品コード1件という単純な1対1設計は禁止。**

FLAM連携詳細は後工程で確定する。

## 17.5 V2マスタで検討するFLAMコード

- FLAM商品との将来マッピングに必要な識別情報（1対1ではない）
- FLAM得意先コード
- FLAM納入先コード

現行kintoneマスタには入っていない。

# 18. 新旧切替方針【確定】

既存本番アプリは開発中に変更しない。

V2を別アプリとして構築・テストする。

切替は、2つの異なる日付で行う。

## 18.1 システム移行日T

- 事前検証済みのV2へ、なすといちごを同じ日に切り替える。先行する品目は作らない。
- 旧アプリの受注・出荷レコードは、出荷済・未出荷を問わず一件もV2へ移行しない。
- T以降の新規受注はV2を正本とする。受注の二重入力はしない。
- T前に旧アプリで受けた未出荷受注は、旧アプリで出荷完了まで処理する。V2へ再入力・移行しない。
- 旧アプリは、旧受注が完了するまでの例外的な継続のみ。新規受注を旧アプリにも入力する並行二重運用はしない。対象受注の出荷が終われば原則参照専用とする。
- V2モニターはTから使用する。T前は現行の紙運用。
- マスタは別扱いとする。受注・出荷データを移行しないことは、必要なマスタ情報を調査・クレンジングしてV2へ整備することを否定しない。
- 旧アプリは過去実績参照用として残す。

## 18.2 正式在庫管理開始日S

- SはTとは別の管理上の開始日とする。旧アプリの未出荷受注がすべて完了し、実棚卸・補正を行う時点で設定する（S ≧ T。TとSが異なる暦日であることは要件としない）。
- T〜S前はV2在庫が実物と一致しない可能性がある暫定期間。V2在庫を確定値として扱わない。
- Sに実棚卸・数量確認を行い、確定済みの在庫管理軸ごとに正しい残高を履歴付きで登録する（§14.7）。
- S以降のV2在庫を正式な管理数値とする。Sより前に遡って、V2在庫が正しかったものとして扱わない。

## 18.3 本番切替までに解決すべき運用上の確認事項（未確定）

- 旧アプリに未出荷受注が残る間（T〜旧受注完了）、V2モニターの必要数量には旧受注分が含まれない可能性がある。
- 旧受注を移行しない方針は維持する。
- 現場が旧受注分を見落とさないための運用方法は未決定。切替手順書で定める。

理想【方向】:

- 業務影響の少ない日曜日等に切替
- 翌営業日からV2運用開始

> v0.2の「切替時点で必要な未処理受注のみ移行する案を検討」を置き換える。

# 24. Claude Codeに必ず守らせる前提

Claude Codeが設計・実装を行う際は以下を前提とする。

1. 旧本番アプリを直接変更しない。
2. V2を新規構築する。
3. 選果場受注と産直受注は統合する。
4. 「発注」機能は廃止する。
5. 出荷区分は受注明細単位（選果場出荷 / 産直出荷）。標準値は出荷先×商品から自動設定。
6. 出荷区分は出荷先固定ではない。
7. 受注管理と出荷管理は分ける。
8. 統合受注管理V2は1レコード=1受注明細。業務項目の組み合わせを一意キーにせず、受注明細IDで識別する。
9. 出荷管理V2は1レコード=1物理発送。出荷IDで識別する。対象は選果場出荷だけで、予定出荷は選果場出荷の受注登録時に自動生成する。
10. 産直出荷は出荷管理V2に登録しない。統合受注管理V2で担当者が手動で出荷済を登録する。
11. なす・いちごは同じ便・送り状・出荷レコードに混載しない。出荷管理V2は共通アプリで、レコード・画面は品目別。
12. 代表送り状番号は1物理発送につき最大1件（空欄可）。
13. 出荷Lotは1実出荷明細に複数可。使用数量はFIFOで自動配分する。
14. 受注状態は有効/キャンセル、出荷状態は未出荷/出荷済。「追加」は状態にしない。キャンセルで数量を0にしない。
15. 重要な受注変更は受注変更履歴に残す。出荷完了後の記録誤りは履歴と在庫差分で訂正する。無履歴の上書きはしない。
16. 業務を止めない。不整合は警告＋理由記録で続行可能とし、重複ID・データ破壊・識別不能につながる操作のみ強く制限する。
17. 数量単位はなす＝ケース、いちご＝パック。いちごの230g換算は生産者間の配分・公平性比較にだけ使う。
18. 仕切りは、なす仕切り管理V2・いちご製造計画V2・いちご受託加工管理V2（SF買取仕切りを内包）に分ける。
19. いちごの週次製造目標は、苺流通システムのアライド向けSF選果場振り分け分とその他販売先の選果場出荷分を合算する。生産者別SF買取目標はSF選果場向け振り分け比率で配分する。販売先別SKUの割当は選果場が判断し、システムで固定しない。
20. いちご完成SKUは全量を受託加工実績とする。SF買取SKUだけ人の買取確定後にSF在庫へ入庫する。生産者返却SKUはSF在庫に入れず、引渡・未返却を追跡しない。
21. 産直出荷は選果場モニター・選果場在庫の対象外。
22. 選果場出荷でもモニター対象外の商品がある。モニター対象は出荷区分だけで判定しない。
23. モニターはなす（ケース）・いちご（パック、販売先別）を別画面とし、受注明細ではなく規格別必要量を出す。Tから使用する。
24. 商品名先頭番号を分類キーに使わない。
25. `senkajo_dx_target` はユーザーが意図的に追加した既存フィールド。
26. 商品Lot・在庫Lot4桁を一意キーにしない。
27. なすのケース入り数違いは別物理SKU。在庫を減らすのは実出荷の物理SKUで、SF所有在庫の管理対象と判定されたものだけ。対象外でも出荷完了・出荷済更新は行う。
28. 初期在庫イベントは「入庫（なす仕切り確定 / いちご買取確定）/ 出荷 / 在庫調整」。厳密な詰替・変換履歴は初期版では要求しない。
29. なす完成品在庫は物理SKU×実日付×日付Lotのケース数、半端在庫は規格×実日付×日付Lotの本数（FIFO）。生産者番号はなすの在庫管理軸にしない。C品在庫はケース、C品の仕切りはkg。
30. いちごSF在庫は生産者×物理SKU×パック詰め日のパック数（FIFO）。販売先別の所有・独占引当にしない。
31. 旧受注・旧出荷は0件移行。なす・いちごは同じシステム移行日Tに切り替える。正式在庫管理開始日SはTとは別の管理上の開始日で、旧アプリの未出荷受注がすべて完了し実棚卸・補正を行う時点で設定する（異なる暦日であることは要件としない）。Sに確定済みの在庫管理軸ごとに棚卸・補正する。T〜S前の在庫は暫定値。
32. T〜旧受注完了の間のモニター上の旧受注の扱いは未決定。運用方法を独断で決めない。
33. kintone商品とFLAM商品を1対1で設計しない。
34. 人が同じ情報を複数アプリへ再入力する設計を避ける。

| 在庫イベント | 仕切入庫 / 出荷 / 在庫調整 | 入庫（なす仕切り確定 / いちご買取確定）/ 出荷 / 在庫調整 |
| いちご在庫 | 範囲未確定 | SF買取確定品のみ。生産者×物理SKU×パック詰め日、パック、FIFO |
| いちご加工 | 定めなし | 全完成SKUを受託加工実績。SF買取は人の確定後に入庫。返却品は追跡しない |
| 商品マスタ属性 | 1ケース当たりパック数を含む | 販売商品/物理SKUフラグ、数量単位、1ケース内容数量、1パック内容重量、加工後取扱区分、仕切り区分等を追加。1ケース当たりパック数は削除 |
| FLAM | 1対1禁止、詳細は後工程 | ＋変換軸（販売商品×得意先×納品日）と有効期間ルールの方向。マッピング不備時はFLAM出力だけ停止 |
| Sでの棚卸 | 定めなし | 確定済みの在庫管理軸ごとに正しい残高を登録 |
| 出荷時の在庫減算 | 選果場在庫の対象分 | SF所有在庫の管理対象と判定された実出荷物理SKUのみ（明確化） |
| 6桁出荷Lot | 構成のみ記載 | なすの現行運用と明記。いちごは要調査（明確化） |
| なす半端在庫 | 規格×実日付×日付Lot、本数、FIFO | 変更なし（維持） |
| 出荷区分の値 | 選果場出荷 / 産直出荷 | 変更なし（統合案の「産地出荷」は採用しない） |
