この文書は、選果場DXについてこれまでのヒアリング、既存kintoneアプリ調査、Claude CodeによるAs-Is調査、設計上の意思決定を、2026-10-08時点で一つに統合した基準文書である。

選果場で現在行っている紙・Excel・複数kintoneアプリ・販売管理ソフトへの二重入力を整理し、kintoneを中心に以下を合理化する。

- 仕切り実績のタブレット入力

- 出荷処理

- 送り状番号管理

- 将来的なFLAMとのデータ連携
- 二重入力・二重管理の削減

導入予定UI:

- 大型モニター 1台
- タブレット 3台

モニター・タブレットはDBではなくUIとして扱う。

# 3. 現行システムの重要なAs-Is

## 3.1 現在確認されている主要kintoneアプリ

- 受注管理（選果場出荷物）
- 受注管理（産直出荷物）
- 青果物商品マスタ
- 青果物出荷先マスタ
- 顧客情報（得意先マスタ）
- なす生産者リスト（生産者マスタ）

## 3.2 受注管理（選果場出荷物）

基本粒度（現行）:

> 1レコード = 出荷予定日 × 出荷先 × 商品

数量単位:

> ケース（c/s）

主な機能:

- 受注登録
- 数量変更
- 追加注文
- キャンセル
- 出荷予定一覧
- 本日出荷計画
- 集計
- 送り状出力
- 出荷Lot入力
- 出荷済管理

受注登録方法:

- 得意先ごとにCSV取込または手入力
- 同じ得意先では概ね方式が固定
- 一部得意先からは1週間分のExcelを受領し、社内でkintone取込用に組み替えている

追加注文:

- 既存レコードの数量を変更
- 現行では「出荷」ラジオボタンの「追加」を使用することがある

問題点:

- 「未出荷 / 出荷済 / キャンセル / 追加」が同一状態フィールドに混在
- 「追加」は本来、出荷状態ではなく受注数量変更
- 現行「本日出荷計画」グラフは「追加」を除外する可能性がある

V2ではこの状態設計をそのまま引き継がない。

## 3.3 受注管理（産直出荷物）

Claude Code調査結果:

- 選果場側と同じ元アプリから派生したと見られる
- JS / CSS / プラグインなし
- 項目数は選果場側より大幅に少ない
- 共通主要項目:
  - 受注日
  - 商品名
  - 受注数量(c/s)
  - 出荷予定日
  - 納品日
  - 出荷先
  - 得意先
- 産直側固有:
  - 発注
  - 出荷確認
  - 備考

### 「発注」ラジオボタン

- アプリ作成当初は使用していた
- 現在は全く使用していない
- 現場ヒアリングでも不要と確認済み
- V2では廃止する

ただし既存アプリでは一覧・グラフの絞り込み条件に使われているため、既存設定をそのままV2へ移植しない。

### 「出荷確認」

- 産直側では現在使われていない
- 選果場側では出荷確認・出荷状態に相当する運用は使っている

V2では受注状態とは分離し、出荷処理側の業務として扱う。

## 3.4 現行2アプリの統合判断

現場ヒアリングにより、同じ商品でも出荷先や取引条件によって

- 受注管理（選果場出荷物）
- 受注管理（産直出荷物）

に分かれていることが判明した。

2アプリ間の業務構造は共通性が高く、産直固有の「発注」機能も不要となっているため、V2では統合する。

## 3.5 送り状・送り状番号（現行運用）

- 現行ではkintoneからCSVを書き出し、ヤマト・佐川・その他該当ソフトの送り状発行ソフトへインポートしている。
- ヤマトは複数個口では1個口ごとに異なる伝票番号が発行される。現在のkintoneでは最若番のみ記録している（2026-10-08 現場確認）。
- 佐川は送り状番号1件。個口数が減る場合は佐川側システムで修正・再発行している。
- その他便では伝票番号自体が存在しない場合がある。

> 確認事項：As-Is調査（docs/10_as_is/ORDER_APP_AS_IS.md §14）では、受注管理アプリに送り状番号を保持するフィールドは確認されていない。最若番の記録先は確認が必要。

# 4. V2全体アーキテクチャ

現時点の第一案は以下。

1. 商品マスタV2
2. 顧客マスタV2
3. 出荷先マスタV2
4. 生産者マスタV2
5. 統合受注管理V2
6. 仕切り管理V2
7. 出荷管理V2
8. 在庫管理V2

既存アプリを直接改修せず、V2を別アプリとして構築する。

## 4.1 各アプリの役割

### 商品マスタV2

「何の商品か」「選果・在庫・出荷・モニター上どう扱うか」を定義する。

### 顧客マスタV2

取引先・FLAM得意先コード、標準受注受付経路、標準荷主名等を管理する。

### 出荷先マスタV2

納入先・住所・送り状関連情報、通常得意先、標準納品リード日数等を管理する。

### 生産者マスタV2

生産者情報・生産者Lot等を管理する。

### 統合受注管理V2

> 何を・いつ・どこへ・何ケース出す予定か

を管理する。

### 仕切り管理V2

> 実際に選果・仕切りで何ができたか

を管理する。

### 出荷管理V2

> 実際にどう出荷したか

を管理する。

送り状、出荷Lot、出荷完了などはここに置く。

### 在庫管理V2

> 在庫がなぜ増減したか

を管理する。

## 4.2 V2全体原則【確定】

### 入力の原則

- 同じ情報を複数アプリへ人が二重入力しない。
- 通常値はマスタ・ルールから自動設定し、対象レコードへスナップショット保存する。
- 例外の場合だけ人が修正する。
- マスタとはIDで正式に紐付け、名称は登録時点のスナップショットとして保存する。

### 業務を止めない原則

- システム上の不整合を理由に現場業務を止めない。
- 在庫不足、Lot未入力、送り状番号未入力等は原則として警告し、例外理由を記録すれば続行可能とする。
- データ破壊・識別不能につながる操作のみ強く制限する。

## 4.3 エンティティの関係【確定】

- 受注明細 n : 1 出荷（1物理発送）
- 受注明細 1 : n 受注変更履歴
- 受注明細 1 : n 実出荷明細（通常1:1。AB/BC混合で複数）
- 実出荷明細 1 : n 出荷Lot使用
- 出荷 1 : 0..n 出荷後例外
- 出荷完了 → 在庫管理V2の出荷イベント（実出荷明細基準）

# 5. 統合受注管理V2

詳細は業務データモデル §3。

## 5.1 レコード粒度【確定】

> 1レコード = 1受注明細

- 同一の **得意先 × 出荷先 × 出荷予定日 × 納品日 × 商品 × 出荷区分** であれば、追加注文が来ても別レコードを作らず数量を集約する。
- 発送元が異なる場合等、同一物理発送にならない場合は別明細とする。
- この組み合わせ自体を一意キーにしない。別途、不変の `受注明細ID` を自動採番する。

> v0.1の「1レコード = 出荷予定日 × 出荷先 × 商品」を置き換える。

## 5.2 受注数量【確定】

- 通常受注はケース（c/s）単位。
- サンプルは商品によって単位が異なるため、統合受注管理V2の対象外とする。
  - 将来別管理する候補。ただし発送は出荷管理V2へ統合できる構造を想定する。

## 5.3 主なフィールド【確定】

- 受注明細ID
- 受注日
- 出荷先ID / 出荷先名
- 得意先ID / 得意先名
- 出荷予定日
- 納品日
- 商品ID / 商品名
- 受注数量(c/s)
- 出荷区分
- 発送元ID / 発送元名
- 初回受注受付経路
- 登録方法
- 受注状態
- 出荷状態
- 出荷ID
- 元受注明細ID
- 受注備考

名称等はマスタIDで正式紐付けし、名称は受注時点のスナップショットとして保存する。

kintoneのフィールド型・フィールドコードは技術設計で決める。

## 5.4 自動設定ルール【確定】

| 項目 | ルール |
|---|---|
| 受注日 | kintoneへの登録日ではなく、実際に得意先から注文を受けた日。登録日時はkintone標準の作成日時等で別管理 |
| 得意先 | 出荷先を選ぶと出荷先マスタの「通常得意先」を自動設定。受注明細へ正式保存し、例外時は変更可能 |
| 納品日 | 出荷先マスタの「標準納品リード日数」で出荷予定日から自動計算。例外時のみ修正。複雑な土日祝配送カレンダーは初期版では不要 |
| 出荷区分 | §5.5 |
| 発送元 | 選果場出荷 → 選果場。産直出荷 → 商品等から標準発送生産者を自動設定。独立フィールドとして保持（同じ産直商品を複数生産者が発送する通常運用は現状ない） |
| 初回受注受付経路 | FAX / 電話 / メール / LINE / WEB / その他。得意先マスタの標準値から自動設定し、例外のみ修正 |
| 登録方法 | 手入力 / CSV取込 / 将来自動連携 等。システムが自動記録。受付経路とは別概念 |

## 5.5 出荷区分【確定】

受注明細ごとに明示的な `出荷区分` を持つ。

値:

- 選果場出荷
- 産直出荷

### 重要

`出荷区分` は出荷先ごとに固定ではない。同じ出荷先でも注文によって選果場出荷と産直出荷が変わる可能性がある。

- 出荷先マスタの固定属性だけでは管理しない
- 受注明細ごとの属性として保存する
- 商品名や商品先頭番号から推定しない

### 標準値

- 標準値は **出荷先 × 商品** の組み合わせから自動設定する。
- 未登録の組み合わせでは担当者が選択し、必要なら営業へ確認する。
- その決定を今後の標準値として登録可能とする。
- 今回だけ例外変更した場合は標準値を自動変更しない。
- 組み合わせ依存ルールのため、商品マスタ単体に持たせない。管理UIは未確定。

## 5.6 状態管理【確定】

旧アプリの状態設計をそのまま引き継がない。

| 状態 | 値 |
|---|---|
| 受注状態 | 有効 / キャンセル |
| 出荷状態 | 未出荷 / 出荷済 |

値はこれのみとする。

### 追加注文

「追加」は状態にしない。

例: 4ケース → 6ケース であれば、受注数量を6へ変更し、受注変更履歴に残す（§5.8）。

## 5.7 キャンセル・削除【確定】

- 正式受注は削除しない。
- 全量キャンセルでも元の受注数量を保持し、`受注状態 = キャンセル` とする。数量を0へ書き換えない。
- 削除を許可するのは以下等のみ。
  - 二重登録
  - テスト登録
  - 明らかな誤登録
  - 実際には受注が存在しなかったデータ

## 5.8 受注変更履歴【確定】

数量変更だけでなく、数量・出荷予定日・納品日・商品・出荷先・得意先・出荷区分・発送元・キャンセル等の重要変更を「受注変更履歴」として残す。

扱う項目:

- 変更日時
- 変更者
- 変更対象
- 変更前
- 変更後
- 数量の場合の増減量
- 変更理由
- 受付経路
- 外部注文番号・発注番号
- 備考

変更前後、変更日時、変更者等は極力自動記録する。人に入力させるのは原則として変更理由のみ。

具体的な実装方式は未確定（技術設計）。

> v0.1の「変更履歴はkintoneの履歴等で追跡できる」を置き換える。kintone標準の変更履歴だけに依存しない。

## 5.9 重複受注【確定】

同一条件の有効受注明細が存在する場合、自動新規登録・自動加算しない。

担当者に以下を提示する。

- 追加発注として加算
- 既存受注を開く
- 中止

追加を選んだ場合だけ既存数量へ加算し、変更履歴を残す。

## 5.10 Excel / CSV【確定】

初期版では以下とする。

- 週次Excel = 初回受注の一括登録
- その後の追加・減数 = LINE・電話等による既存受注変更
- 同一取込データの二重取込を警告・防止
- 修正版Excelは例外的な訂正

修正版Excelの高度な自動差分反映は初期版必須ではない。

## 5.11 欠品追送【確定】

- 欠品時は得意先へ連絡し、元受注数量を当日出荷可能数量へ修正する。
- 不足分の追送を顧客が希望した場合は、翌日以降の別受注明細として登録する。
- 追送明細には `元受注明細ID` を保持する。

## 5.12 産直「発注」機能【確定】

廃止確定。

- 未発注
- 発注済
- キャンセル（未手配）
- キャンセル（手配済）

という旧概念はV2に引き継がない。キャンセルは受注状態として管理する。

## 5.13 備考

共通の `受注備考` を持つ【確定】。

# 6. 受注管理と出荷管理の分離・予定出荷

## 6.1 分離理由【確定】

受注と出荷ではレコード粒度と業務責任が異なる。

- 統合受注管理V2：何を出す予定か（1受注明細）
- 出荷管理V2：実際にどう出荷したか（1物理発送）

送り状番号・個口数・荷主名・物流業者は物理発送単位の情報であるため、受注明細に重複保持せず出荷管理V2に置く。

## 6.2 二重入力はさせない【確定】

アプリは分離するが、受注情報を人が出荷管理へ再入力する設計にはしない。

出荷管理で人が入力するものは、実出荷時にしか分からない情報を中心とする。

- 代表送り状番号
- 出荷Lot（使用数量はFIFOで自動配分）
- 特殊梱包時の確定個口数
- 実出荷内容に差異がある場合の補正（AB/BC分解を含む）
- 出荷完了

## 6.3 予定出荷の自動生成【確定】

- 受注登録時に出荷管理V2の予定出荷レコードを自動生成する。
- 既存未出荷レコードが存在すれば自動的にそこへ紐付ける。
- 通常の自動グルーピング条件:

> 出荷日 × 納品日 × 出荷先 × 得意先 × 発送元

- 得意先を含める理由は、同一出荷先でも帳合先が異なる荷物を同一送り状へまとめないため。
- この組み合わせを一意キーにしない。正式識別子は `出荷ID`。
- 特殊事情では同条件でも複数物理発送を許容する。
- 未出荷中の受注変更は予定出荷へ自動追従する。

## 6.4 出荷完了と受注明細【確定】

出荷管理V2の出荷完了により、関連する受注明細を自動で出荷済に更新する。受注管理側で別途手動で「出荷済」を二重入力しない。

# 7. 出荷管理V2

詳細は業務データモデル §5〜§8。

## 7.1 レコード粒度・状態【確定】

> 1レコード = 1物理発送

- 受注登録時点から「予定出荷の器」として存在し、出荷時に実績情報を加え、出荷完了によって実績として確定する。
- 状態は 未出荷 / 出荷完了 のみ。中間状態は持たない。

> v0.1の「基本粒度 = 出荷日 × 出荷先」を置き換える。

## 7.2 主なヘッダ情報【確定】

- 出荷ID
- 出荷日
- 納品日
- 出荷先ID / 出荷先名
- 得意先ID / 得意先名
- 発送元ID / 発送元名
- 荷主名
- 物流業者
- 自動計算個口数
- 確定個口数
- 代表送り状番号
- 送り状CSV出力日時 / 出力者
- 送り状番号登録日時 / 登録者
- 出荷状態
- 出荷完了日時
- 出荷完了者
- 出荷備考
- 例外完了情報
- 出荷後例外情報

## 7.3 荷主名・物流業者【確定】

- 荷主名：得意先ごとに標準値を持ち自動設定。一部得意先では得意先名にする必要がある。例外時のみ出荷管理側で変更可能。
- 物流業者：発送元 × 出荷先 でほぼ決まる。標準値を自動設定し、荷量偏り等の例外時のみ変更する。同一日の同一発送をヤマト・佐川に分割する通常運用はない。

## 7.4 個口数【確定】

- 商品によって何ケースで1個口かが異なる。異なる商品でも同じ梱包グループなら一緒に縛る場合がある。
- 商品マスタV2等に「個口計算グループ」「標準ケース数/個口」を持たせる。
  - 例：A長1cs ＋ B品1cs、同じ「なす通常箱」グループ（2cs/個口）→ 1個口
- 出荷管理V2に「自動計算個口数」「確定個口数」を持つ。通常は自動値、特殊梱包時のみ手修正。

## 7.5 実出荷明細【確定】

通常は受注明細から自動生成する。

> 通常：1受注明細 → 1実出荷明細

受注内容と同じなら現場は触らない。

扱う項目:

- 実出荷明細ID
- 元受注明細ID
- 受注商品ID / 名称
- 実出荷商品ID / 名称
- 実出荷数量(c/s)
- 差異区分
- 差異理由
- 明細備考

## 7.6 受注数量と実出荷数量【確定】

通常:

> 受注数量 = 実出荷数量

欠品が発生する場合は取引先へ連絡し、受注数量そのものを修正する（追送は別受注明細、§5.11）。

出荷処理側で独自に「受注10、実出荷8」のような減数を通常運用にしない。

## 7.7 出荷完了【確定】

出荷完了はトラック出発後・Lot入力後に実行する。

完了操作により以下を自動実行する。

1. 出荷管理V2を出荷完了
2. 実出荷明細を基準に在庫管理V2へ出荷イベントを作成（選果場在庫の対象分）
3. 関連する統合受注管理V2を出荷済へ更新

完了日時・完了者は自動記録する。

## 7.8 例外完了【確定】

以下のような場合も原則として業務を止めない。

- システム在庫不足
- Lot未入力
- 代表送り状番号未入力
- 個口数未確定
- 混合商品の数量不一致
- その他情報不足

- 警告内容はシステムが自動記録する。
- 人は例外理由を選択し、必要時のみ備考を入力する。
- 例外完了日時・実行者を自動記録する。
- 一時的に理論在庫がマイナスになっても、実際に出荷した事実の記録を優先する。

## 7.9 出荷後例外【確定】

- 出荷完了後の重要項目は原則修正不可。
- 顧客がキャンセル連絡を忘れており出荷後に停止依頼が来るケース等は、元の受注・出荷を取消すのではなく出荷後例外として記録する。
- 例外種別例：配送停止 / 営業所引取 / 返送 / 別販売 / 廃棄 / その他
- 商品が戻り再販売可能となれば在庫管理V2で在庫調整する。
- 専用アプリは作らず、初期版では出荷管理V2の付帯情報で十分。

## 7.10 送り状CSV【方向】

- V2では送り状CSVの出力元を出荷管理V2とする方向。
- 物流業者ごとのCSVレイアウトは後の技術設計・現物確認で確定する。

# 8. 出荷Lot

## 8.1 現行仕様

出荷Lotは6桁。

構成:

1. 商品Lot 2桁
2. 日付Lot 2桁
3. 生産者Lot 2桁

例:

`商品Lot + 日付Lot + 生産者Lot`

## 8.2 日付Lot

日付 + 10。

月は含まれないため、翌月同日で同じ番号になることがある。

## 8.3 特徴

- 通し番号ではない
- 同日・同生産者・同商品は同じLot
- 「こづち」機械でアナログ6桁スタンプを貼付
- 1受注明細が複数Lotにまたがる可能性あり
- 現在も実運用で使用している
- 入力はトラック出発後に行う運用
- 選別時、半端の入った箱にはLot番号を2枚付ける場合がある

## 8.4 V2での扱い【確定】

- 商品ごとに「出荷Lot管理対象 / 対象外」を持つ。Lot管理対象商品のみLot入力を通常要求する。
- 1実出荷明細に複数Lotを許容する。
- 商品Lotを一意キーにしない。
- Lot別使用数量はデータとして持つが、現場には原則入力させない。
  - 在庫の古い日付からFIFOでシステムが自動配分し、実態と異なる場合だけ修正する。
- Lot入力UI・FIFO自動配分UIは未確定（技術設計）。

## 8.5 優先度

トレーサビリティの高度化は当面の最優先課題ではない。

まずはDB構造と管理業務の合理化を優先する。

将来的にタブレットカメラによる数字OCRも検討可能。

# 9. 送り状番号【確定】

- 送り状番号は商品明細単位ではなく、物理発送単位。受注明細ではなく出荷管理V2に置く。
- 物流業者ごとの実態（§3.5）に基づき、正式表現を以下とする。

> **V2では1物理発送につき代表送り状番号を最大1件保持する。**

| 物流業者 | V2での扱い |
|---|---|
| ヤマト | 最若番を代表送り状番号として1件保存。全番号管理はしない。個口数が減った場合は減った分の伝票を廃棄する |
| 佐川 | 1件記録する。個口数が減る場合も佐川側システムへ修正を入れて再発行する |
| その他便 | 伝票番号が存在しない場合があり、空欄可 |

- ヤマト・佐川では通常入力するが、業務を止めない原則により、緊急時は警告＋理由記録で出荷完了可能とする。
- 送り状バーコードは存在するため、将来的にタブレットカメラで読み取る方向を検討する【方向】。

> v0.1の「出荷先単位」「同一出荷先で10個口でも送り状番号は1つ」は、現場再確認により訂正した。

# 10. 選果場大型モニター

## 10.1 最重要要件

大型モニターに表示するのは受注明細そのものではない。

表示したいのは:

> **本日、選果場でどの規格がどれだけ必要か**

という規格別必要数量。

## 10.2 対象品目と画面【確定】

当面:

- なす
- いちご

なすといちごは完全に別画面とする。Source of Truthはどちらも統合受注管理V2。

### なす

- 規格別の必要ケース数。
- 入り数違いの物理SKUでも、同じ `モニター集計規格` にまとめる（例：A長80本入・A長70本入 → A長）。
- AB/BCは初期版ではA/B等へ事前配分せず、`AB混合 ○cs` のまま混合規格名でケース表示する。

### いちご

- 規格別の必要パック数。
- 統合受注管理V2の受注数量はケースのまま保持する。
- 商品マスタの `1ケース当たりパック数` で必要パック数へ換算する。
- 1ケース当たりパック数は商品ごとに固定。

## 10.3 「選果場出荷」と「モニター対象」は別概念【確定】

重要:

> 選果場出荷であっても、選果場で選果・規格調整を行わない商品がある。

例:

- 産地から持ち込まれたものを、そのまま出荷する商品

これらは「選果場出荷」ではあるが、規格別必要量を表示するモニター集計の対象には含めない。

したがって:

`出荷区分 = 選果場出荷`

だけではモニター対象を判定しない。

## 10.4 モニター対象判定【方向】

商品マスタ等に明示的な属性を持たせる。属性名は候補。

- モニター集計対象
- 品目
- モニター集計規格
- モニター集計単位
- 1ケース当たりパック数

## 10.5 モニター用DBの考え方【確定】

モニター情報を人が別途手入力するSource of Truthにはしない。

基本:

> 統合受注管理V2の有効受注
> → 商品マスタの集計属性で対象判定
> → 規格別必要数量へ集計（いちごはパック換算）
> → モニター表示

派生データとして扱う。

## 10.6 産直出荷

産直出荷は選果場モニター対象外。

# 11. 商品マスタ

## 11.1 現行の商品名先頭番号ルール

トップページでは以下のルールが案内されていた。

- 1. 筑陽なすA品
- 2. 筑陽なすA品以外
- 3. とろとろ炒めなす
- 4. 選果場出荷その他野菜果物
- 5. 産地直送野菜果物
- 6. その他

当初は「1〜3 = なす」として利用できる可能性を考えた。

## 11.2 実データとの不整合

実データではこの命名ルールが守られていないことが判明した。

例:

- 15.
- 17.

などが存在。

したがって:

> **商品名先頭番号をDX対象判定・在庫判定・モニター判定の機械的キーとして使用しない。**

## 11.3 選果場DX対象フィールド

現行商品マスタにユーザーが意図的に追加済み。

- フィールド名: 選果場DX対象
- フィールドコード: `senkajo_dx_target`
- 選択肢:
  - 対象外
  - 対象
- 初期値:
  - 対象外

この追加は意図した変更である。

## 11.4 なす物理SKU【確定】

これまでkintoneでは、ケース入り本数が変わっても同じ商品として扱っていた。

しかし、

- 入り数は時期により2段階
- 切替時期は毎年おおむね同じだが微妙に前後する
- 同じ出荷日でも取引先によって旧入り数 / 新入り数が混在し得る

ことが確認された。

したがってV2では、

> **ケース入り数が異なるものは別物理SKUとして商品マスタV2へ登録する。**

例:

- A長80本入
- A長70本入

受注・出荷・完成品在庫も別SKUで管理する。一方、モニター集計規格は両方とも `A長` にできる。

## 11.5 AB混合・BC混合【確定】

- AB混合・BC混合は販売商品として今後も販売可能。廃止商品ではない。
- 選果場の確定方針として、物理的な混合箱は作らない。
- 受注例：AB混合 10cs → 実出荷例：A品 6cs ＋ B品 4cs
- 配分比率は固定しない。その日の出来高・在庫状況で決定する。
- 商品マスタ側で「許容実出荷商品」を定義する。
  - AB混合 → A品・B品のみ許容
  - BC混合 → B品・C品のみ許容
- 混合商品の分解は正常運用なので差異理由を人に入力させない。
- 在庫を減らすのは受注商品ではなく実出荷商品。
- モニター初期版ではAB/BCを事前配分せず `AB混合 ○cs` のまま表示する（§10.2）。

> v0.1の「取引商品・受注商品としてAB混合 / BC混合が残る可能性はある」を、「販売商品として継続」に確定した。

## 11.6 商品マスタV2へ引き継ぐ属性【方向】

商品マスタ詳細設計へ送るもの（属性名は候補、型・値は詳細設計で確定）:

- 商品ID
- 商品名
- 品目
- 選果場DX対象
- 物理SKU
- ケース入り数
- 標準発送元
- 出荷Lot管理対象
- 許容実出荷商品
- モニター集計対象
- モニター集計規格
- モニター集計単位
- 1ケース当たりパック数
- 個口計算グループ
- 標準ケース数/個口
- 商品Lot
- FLAMとの将来マッピングに必要な識別情報

注意:

- 出荷先×商品の標準出荷区分等、組み合わせ依存ルールを商品マスタ単体へ無理に持たせない【確定】。
- v0.1で候補としていた「在庫管理対象」「等級区分」「在庫商品区分」の要否は、商品マスタ・在庫管理V2の詳細設計で判断する（未確定）。
- v0.1の候補「FLAM商品コード」は、1対1設計禁止（§17.4）により「FLAMとの将来マッピングに必要な識別情報」に置き換えた。

# 12. 商品Lot

商品Lotは商品マスタ内のフィールドであり、独立したマスタではない。

重要:

- SKUの一意キーではない
- 複数商品で同じ商品Lotが存在する
- 空欄の商品もある
- 在庫グループのキーと決めつけない
- 正確な業務意味は完全には確定していない

V2で一意キーとして使用しない。在庫Lotの4桁表示（§14.4）の一部として現場表示に使うことはある。

# 13. 仕切り管理V2

基本案:

> 1レコード = 仕切日 × 生産者

サブテーブル等で複数商品をまとめて入力できる形を検討する。

候補項目:

- 商品
- ケース数
- 半端本数
- kg
- その他必要な実績

仕切り登録を在庫増加の根拠とする。

生産者は既存の「なす生産者リスト」を調査し、V2生産者マスタへ整理する。

C品の仕切り入力単位:

- 在庫管理単位はケースとした（§14.3）が、仕切り入力時のC品実績をkgで入力する現行運用まで廃止するとは確定していない。
- 仕切り管理V2のC品入力単位はケースへ独断で変更せず、仕切り設計時の確認事項とする（未確定）。

詳細フィールド設計は現物の仕切り用紙・実際の運用を確認して決める。

# 14. 在庫管理V2

## 14.1 基本方針

初期版では運用負荷を最小化する。

在庫イベントは以下の3つに簡略化する【確定】。

1. 仕切入庫
2. 出荷（出荷完了時に実出荷明細を基準に自動作成）
3. 在庫調整

一時的に理論在庫がマイナスになっても、実際に出荷した事実の記録を優先する【確定】。

産直出荷は選果場在庫の対象外【確定】。

## 14.2 在庫調整で扱うもの

- 80本入り → 3本パック等への作り替え
- 詰め替え（80本入 → 70本入 等）
- 検品ロス
- 傷み・廃棄
- 数量訂正
- 出荷後例外で戻り、再販売可能となった商品
- その他差異

初期版では厳密な製造変換履歴を持たない。

## 14.3 在庫単位【確定】

| 在庫区分 | 管理軸 | 数量単位 |
|---|---|---|
| 完成品在庫 | 物理SKU × 実日付 × 日付Lot | ケース |
| 半端在庫 | 規格 × 実日付 × 日付Lot | 本数 |

- 半端もFIFO対象である。規格だけで集約して日付を失わないこと。
- 生産者番号は在庫管理軸にしない。
- 半端は翌日へ持ち越す。
- C品も在庫管理はケース単位でよい。

例：80本入1cs（実日付D・日付Lot L）を70本入へ詰め替え

- 80本入SKU（D・L）−1cs
- 70本入SKU（D・L）＋1cs
- 半端（A長・D・L）＋10本

> v0.1の「A/B品は内部本数ベース（例：80本入り5ケース+18本 = 418本）」「C品はkg管理、C品kg在庫は翌日へ持ち越す」を置き換える。

## 14.4 なす在庫Lot【確定】

- 在庫段階では生産者番号は管理不要。必要なのは「実日付・日付Lot + 物理SKU（完成品）/ 規格（半端）」。
- 現場表示は「商品Lot2桁 + 日付Lot2桁 = 4桁」を使用可能。ただし4桁自体をDB一意キーにしない。
- 日付Lotは月を含まず翌月同日に重複するため、日付Lotだけでなく実際の暦日（実日付）を管理軸に含める（§14.3）。
- 同じ管理軸なら、生産者が異なっても在庫は合算する。

## 14.5 詰め替え・半端とLot【確定】

- 初期版では厳密な製造変換履歴を作らず「在庫調整」で扱う。
- 80→70本等の詰め替えで半端を組み合わせて箱を作る場合は古い日付を採用する。
- 現物ラベルの生産者番号は `00` とする（生産者番号は在庫管理軸ではない）。
- FIFO上の年齢をリセットしない。システム内部でも、詰め替え後の在庫は元在庫のうち最も古い実日付・日付Lotを引き継ぐ。

## 14.6 3本パック

- 1パック = 3本
- 1ケース = 20パック

実際には選果時に最終形で作ることが多い。

在庫が多い場合、既存商品を出荷日に3本パック等へ詰め替える場合がある。

初期版では厳密な変換トレースはせず、在庫調整で扱う。

# 17. FLAMとの関係

## 17.1 現状

販売管理ソフト:

> FLAM

現状の入力順:

1. kintoneへ先に受注入力
2. FLAMへ再入力

そのため二重入力・二重管理が発生している。

## 17.2 FLAMの役割

現状、集計・販売管理はFLAM側で行っており、kintone受注アプリの集計機能は主要目的ではない。

## 17.3 将来方向

V2では以下を検討する。

> 統合受注管理V2
> → FLAM固定取込フォーマットに合わせたCSV生成
> → FLAMへアップロード

ユーザー契約は最も安いプラン。

CSVレイアウト自由設定が使えない可能性があるため、FLAM側を自由化するのではなく、kintone側からFLAMの固定フォーマットに合わせる方向を第一候補とする。

ただし実装前に、実際の契約プラン・FLAM画面・取込仕様を再確認する。

## 17.4 FLAMとの商品関係【確定】

なすについて、

- kintone物理SKU：入り数差等を表現
- FLAM商品：価格変更により4段階

という別概念である。FLAMの4段階切替も毎年おおむね同時期だが、実際の日付は前後する。

したがって、

> **kintone商品1件 = FLAM商品コード1件という単純な1対1設計は禁止。**

FLAM連携詳細は後工程で確定する。

- FLAM得意先コード
- FLAM納入先コード

現行kintoneマスタには入っていない。

# 19. 既存資産の扱い

既存資産は「そのまま流用」ではなく「要件抽出・As-Is確認」に使う。

特に:

- 既存選果場受注アプリ
- 既存産直受注アプリ
- 既存送り状出力JS
- 既存一覧・グラフ
- 現行商品マスタ
- 出荷先マスタ
- 顧客マスタ
- 生産者マスタ

から、有用な機能・項目のみV2へ再設計して取り込む。

旧フィールドコードは意味が崩れているものがあるため、V2では流用しない。

例:

- 同じ `ラジオボタン_0` が、選果場では「出荷」、産直では「発注」
- 同じコードでも意味が異なる

V2では意味のある英数字フィールドコードを使用する。

## 19.1 本日出荷計画の現状

旧xlsmは現在使っていない。

ただし大型モニターにそのまま「受注明細」を出すのではなく、前述のとおり「選果対象の規格別必要量」へ集計して表示する。

# 24. Claude Codeに必ず守らせる前提

Claude Codeが設計・実装を行う際は以下を前提とする。

1. 旧本番アプリを直接変更しない。
2. V2を新規構築する。
3. 選果場受注と産直受注は統合する。
4. 「発注」機能は廃止する。
5. 出荷区分は受注明細単位（選果場出荷 / 産直出荷）。標準値は出荷先×商品から自動設定。
6. 出荷区分は出荷先固定ではない。
7. 受注管理と出荷管理は分ける。
8. 統合受注管理V2は1レコード=1受注明細。業務項目の組み合わせを一意キーにせず、受注明細IDで識別する。
9. 出荷管理V2は1レコード=1物理発送。出荷IDで識別する。予定出荷は受注登録時に自動生成する。
10. 代表送り状番号は1物理発送につき最大1件（空欄可）。
11. 出荷Lotは1実出荷明細に複数可。使用数量はFIFOで自動配分する。
12. 受注状態は有効/キャンセル、出荷状態は未出荷/出荷済。「追加」は状態にしない。キャンセルで数量を0にしない。
13. 重要な受注変更は受注変更履歴に残す。
14. 業務を止めない。不整合は警告＋理由記録で続行可能とし、データ破壊・識別不能につながる操作のみ強く制限する。
15. 産直出荷は選果場モニター・選果場在庫の対象外。
16. 選果場出荷でもモニター対象外の商品がある。モニター対象は出荷区分だけで判定しない。
17. モニターはなす（ケース）・いちご（パック）を別画面とし、受注明細ではなく規格別必要量を出す。
18. 商品名先頭番号を分類キーに使わない。
19. `senkajo_dx_target` はユーザーが意図的に追加した既存フィールド。
20. 商品Lot・在庫Lot4桁を一意キーにしない。
21. なすのケース入り数違いは別物理SKU。在庫を減らすのは実出荷商品。
22. 初期在庫イベントは「仕切入庫 / 出荷 / 在庫調整」。厳密な詰替・変換履歴は初期版では要求しない。
23. 完成品在庫は物理SKU×実日付×日付Lotのケース数、半端在庫は規格×実日付×日付Lotの本数。生産者番号は在庫管理軸にしない。C品在庫もケース。ただしC品の仕切り入力単位は未確定のまま独断で変えない。
24. kintone商品とFLAM商品を1対1で設計しない。
25. 人が同じ情報を複数アプリへ再入力する設計を避ける。
