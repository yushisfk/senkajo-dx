# 選果場DX

## 目的

選果場に大型モニター1台とタブレット3台を導入する。
現在、紙・Excel・複数のkintoneアプリ・販売管理ソフト（FLAM）に分散している、
出荷情報の掲示、なすの仕切り、いちごの製造計画・受託加工、在庫管理、出荷時の入力、受注管理を、
kintoneを中心に整理・合理化する。

## 基本方針

- kintoneを中心に構築する。
- 既存の本番kintoneアプリは直接改修しない。
  V2を別アプリ群として新規構築し、完成・検証後に切り替える。
- 既存アプリは、As-Is調査・過去データ参照用として扱う。
- 受注管理（選果場出荷物）と受注管理（産直出荷物）を、「統合受注管理V2」に統合する。
  選果場出荷か産直出荷かは、受注明細ごとの「出荷区分」で区別する。
- 受注・仕切り・製造計画・受託加工・出荷・在庫の役割を分ける。
  - 統合受注管理V2：何を、いつ、どこへ、いくつ出す予定か（産直出荷の出荷済登録もここで行う）
  - なす仕切り管理V2：なすの選果・仕切りで、生産者ごとに何ができたか
  - いちご製造計画V2：いちごを週にどれだけ作るか、生産者別にどれだけ買い取る目標か
  - いちご受託加工管理V2：いちごを生産者ごとにどれだけ加工し、そのうち何をSFが買い取ったか
  - 出荷管理V2：選果場出荷を実際にどう出荷したか（送り状番号、出荷Lot、出荷完了など）
  - 在庫管理V2：SF所有在庫がなぜ増減したか（なす・いちご共通）
- 数量の単位は、なすはケース、いちごはパックとする。
- なすといちごは、同じ便・同じ送り状で混載しない。
- 同じ情報を、人が複数のアプリへ二重入力しない。
  通常値はマスタ・ルールから自動設定し、例外の場合だけ人が修正する。
- システム上の不整合（在庫不足、Lot未入力、送り状番号未入力など）を理由に現場業務を止めない。
  警告し、例外理由を記録すれば続行できるようにする。
- 大型モニターは、「本日、選果場でどの規格がどれだけ必要か」を表示するUIとする。
  - 当面の対象品目はなす・いちご。なす（必要ケース数）といちご（必要パック数）は別画面とする。
  - 受注データから自動で生成する。
- タブレットは、なす仕切り・いちご加工・出荷・在庫の現場入力用UIとする。
- 新旧切替では、旧アプリの受注・出荷は1件も移行しない。旧受注は旧アプリで出荷完了まで処理する。
  なす・いちごは同じシステム移行日Tに切り替え、在庫は旧受注の完了後の正式在庫管理開始日Sから正式値とする。
- FLAMへの二重入力の削減（kintoneからFLAM取込データを生成すること）は、将来の検討事項とする。

### GitHubを基準とした連携（2026-11-08〜）

- GitHub（`yushisfk/senkajo-dx`）の master に保存された正式文書を、プロジェクトの基準とする。
- ChatGPTは、接続が利用できる場合、GitHub上の最新版を直接確認する。ローカルの未コミットファイルは確認できない場合がある。
- Claude Codeは、ローカルの変更、技術設計、実装、Git操作を担当する。
- GitHubがまだ更新されていない場合は、未コミットの内容との相違に注意する（PROJECT_STATUS.md の基準コミットを確認する）。
- GitHubへの書き込み（commit・push等）は、ユーザーの承認と既存の開発ルールに従う。
