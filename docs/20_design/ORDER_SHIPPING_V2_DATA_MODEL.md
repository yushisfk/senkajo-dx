## 0. この文書の位置づけ

統合受注管理V2と出荷管理V2の、**業務上のデータモデル**（何を、どの粒度で、どの責任で持つか）を定義する正式文書である。

- 本書は業務データモデルを定める。kintoneのフィールド型、フィールドコード、サブテーブルか別アプリか、画面・JSの方式は定めない（§12）。それらはClaude CodeのPlan Modeによる技術設計で決める。
- 項目名は業務上の名称である。V2のフィールドコードは、技術設計で意味のある英数字により付ける。
- 上位文書と矛盾する場合は、CLAUDE.md の優先順位に従う。上位文書は本書と同期している。

## 1. 全体原則【確定】

### 1.1 Source of Truth

| 情報 | Source of Truth |
|---|---|
| 受注予定（選果場出荷・産直出荷）、産直出荷の出荷済 | 統合受注管理V2 |
| 選果場出荷の実出荷・送り状・出荷Lot・出荷完了 | 出荷管理V2 |
| SF所有在庫の増減履歴 | 在庫管理V2 |
| 商品属性・換算・集計ルール | 商品マスタV2 |
| モニター表示 | 派生情報（統合受注管理V2から生成） |

### 1.2 入力の原則

- 同じ情報を複数アプリへ人が二重入力しない。
- 通常値はマスタ・ルールから自動設定し、対象レコードへ**スナップショットとして保存**する。
- 例外の場合だけ人が修正する。
- マスタとはIDで正式に紐付け、名称は登録時点のスナップショットとして保存する。

### 1.3 業務を止めない原則

- システム上の不整合を理由に、現場業務を止めない。
- 在庫不足、Lot未入力、送り状番号未入力等は、原則として**警告**し、例外理由を記録すれば続行可能とする。
- 強く制限するのは、データ破壊・識別不能につながる操作のみとする。

## 2. エンティティと関係【確定】

```
統合受注管理V2                         出荷管理V2                          在庫管理V2
┌────────────┐ 1   n ┌────────────┐
│ 受注明細    │──────│ 受注変更履歴 │
│ (受注明細ID)│      └────────────┘
└────────────┘
   │ n                 1 ┌─────────────────┐ 1   n ┌──────────────┐ 1  n ┌────────────┐
   └──────────(出荷ID)──│ 出荷（1物理発送）│──────│ 実出荷明細    │─────│ 出荷Lot使用 │
                         │ (出荷ID)        │      │(実出荷明細ID) │     └────────────┘
                         └─────────────────┘      └──────────────┘
                              │ 1                       │ 出荷完了時
                              │ 0..n                    ▼
                         ┌─────────────┐          ┌────────────┐
                         │ 出荷後例外    │          │ 出荷イベント │
                         └─────────────┘          └────────────┘
```

- 受注明細 n : 1 出荷。1受注明細（選果場出荷）は1つの出荷（予定出荷）に紐付く。
- **産直出荷の受注明細は出荷に紐付かない**（`出荷ID` は空）。出荷管理V2・在庫管理V2には何も作らない（§4）。
- 1つの出荷は1品目だけを含む。なす・いちごを混在させない（§5）。
- 受注明細 1 : n 実出荷明細。通常は1:1。AB混合・BC混合では1受注明細から複数の実出荷明細になる（§8.4）。
- 実出荷明細 1 : n 出荷Lot使用。1実出荷明細に複数Lotを許容する（§8.5）。
- 出荷 1 : 0..n 出荷後例外（§8.8）。
- 在庫管理V2の出荷イベントは、出荷完了時に実出荷明細を基準に作成する。対象は在庫管理対象の物理SKUだけ（§8.6）。

## 3. 統合受注管理V2

### 3.1 レコード粒度【確定】

> **1レコード = 1受注明細**

- 同一の **得意先 × 出荷先 × 出荷予定日 × 納品日 × 商品 × 出荷区分** であれば、追加注文が来ても別レコードを作らず、数量を集約する。
- 発送元が異なる場合等、同一物理発送にならない場合は別明細とする。
- この業務項目の組み合わせ自体は**一意キーにしない**。
- 別途、不変の `受注明細ID` を自動採番し、正式な識別子とする。

> 旧前提「1レコード = 出荷予定日 × 出荷先 × 商品」（2026-10-06）を置き換える。

### 3.2 受注数量【確定】

- 数量単位は商品ごとの属性とし、商品マスタの数量単位から自動設定する。**なすはケース（c/s）、いちごはパック（P）**。
- いちごの230g換算パックは、生産者間の配分・公平性比較にだけ使う。受注数量は実パック数で持つ。
- サンプル等、数量単位が特殊な業務は、初期版の通常受注フローと区別する。必要なら後工程で検討する【候補】。

> 旧前提「通常受注の数量単位はケース（c/s）」（2026-10-08）を置き換える。

### 3.3 項目【確定】

業務データモデルとして、少なくとも以下を保持する。

| 項目 | 内容 | 設定方法 |
|---|---|---|
| 受注明細ID | 不変の正式識別子 | システム自動採番 |
| 受注日 | 実際に得意先から注文を受けた日（§3.4） | 入力（取込時は取込データ） |
| 出荷先ID / 出荷先名 | 納入先。名はスナップショット | 選択 |
| 得意先ID / 得意先名 | 帳合先。名はスナップショット | 出荷先マスタの「通常得意先」から自動。例外時変更可（§3.5） |
| 出荷予定日 | | 入力 |
| 納品日 | | 出荷予定日＋出荷先マスタの標準納品リード日数で自動。例外時修正（§3.6） |
| 商品ID / 商品名 | 名はスナップショット | 選択 |
| 受注数量 | 数量単位で表す | 入力 |
| 数量単位 | ケース / パック 等 | 商品マスタから自動 |
| 出荷区分 | 選果場出荷 / 産直出荷 | 出荷先×商品の標準値から自動（§3.7） |
| 発送元ID / 発送元名 | 物理的な発送元 | 出荷区分・商品から自動（§3.8） |
| 初回受注受付経路 | FAX / 電話 / メール / LINE / WEB / その他 | 得意先マスタの標準値から自動。例外時修正（§3.9） |
| 登録方法 | 手入力 / CSV取込 / 将来自動連携 等 | システム自動記録（§3.9） |
| 受注状態 | 有効 / キャンセル | §3.10 |
| 出荷状態 | 未出荷 / 出荷済 | 選果場出荷は出荷完了により自動更新、産直出荷は担当者が手動登録（§3.10） |
| 出荷ID | 紐付く出荷管理V2の出荷（選果場出荷のみ） | システム自動（§4） |
| 元受注明細ID | 欠品追送の元明細 | 追送明細登録時に設定（§3.15） |
| 受注備考 | | 入力 |

- kintone標準の作成日時・作成者・更新日時・更新者は、上記とは別に保持される。

### 3.4 受注日【確定】

- `受注日` は**kintoneへの登録日ではない**。実際に得意先から注文を受けた日とする。
- 登録日時は、kintone標準の作成日時等で別に管理する。

### 3.5 得意先【確定】

- 通常は、出荷先を選ぶと出荷先マスタの「通常得意先」を自動設定する。
- 同じ出荷先でも例外的に別得意先があり得るため、得意先は受注明細に正式に保存し、例外時は変更可能とする。

### 3.6 納品日【確定】

- 出荷先マスタに「標準納品リード日数」を持つ。
- 納品日は出荷予定日から自動計算し、例外の場合のみ修正する。
- 複雑な土日祝の配送カレンダーは、初期版では不要。

### 3.7 出荷区分【確定】

- 受注明細単位で「選果場出荷 / 産直出荷」を保持する。出荷先固定ではない。
- 商品名・商品名先頭番号から推定しない。
- 標準値は **出荷先 × 商品** の組み合わせから自動設定する。
- 未登録の組み合わせでは担当者が選択し、必要なら営業へ確認する。
  - その決定を、今後の標準値として登録可能とする。
- 今回だけ例外的に変更した場合、標準値は自動変更しない。
- 標準値ルールは組み合わせ依存のため、商品マスタ単体に持たせない（§10.3）。管理UIは【未確定】。

### 3.8 発送元【確定】

- 受注明細に発送元を保持する。
  - 選果場出荷 → 選果場
  - 産直出荷 → 商品等から標準発送生産者を自動設定
- 現状、同じ産直商品を複数生産者が発送する通常運用はないが、発送元は独立フィールドとして持つ。
- 発送元IDの参照先（選果場と生産者を同じ参照で扱う方法）は【未確定】（技術設計）。

### 3.9 初回受注受付経路と登録方法【確定】

- 初回受注受付経路：FAX / 電話 / メール / LINE / WEB / その他。
  - 得意先マスタの標準値から自動設定し、例外のみ修正する。
- 登録方法は受付経路とは別の概念で、システムが自動記録する。
  - 例：手入力 / CSV取込 / 将来自動連携
- 2回目以降の変更の受付経路は、受注変更履歴に記録する（§3.12）。

### 3.10 状態【確定】

| 状態 | 値 |
|---|---|
| 受注状態 | 有効 / キャンセル |
| 出荷状態 | 未出荷 / 出荷済 |

- 値はこれのみとする。
- 「追加」は状態にしない。受注数量の変更として扱う。
- 出荷状態の更新：
  - 選果場出荷：出荷管理V2の出荷完了により自動で「出荷済」になる。受注側で手動の出荷済を二重入力しない。
  - 産直出荷：初期版では、事務所等の担当者が統合受注管理V2で手動で「出荷済」を登録する。外部連携の自動化は初期版では必須としない。

### 3.11 キャンセルと削除【確定】

- 正式受注は削除しない。
- 全量キャンセルでも元の受注数量を保持し、`受注状態 = キャンセル` とする。数量を0へ書き換えない。
- 削除を許可するのは、以下等に限る。
  - 二重登録
  - テスト登録
  - 明らかな誤登録
  - 実際には受注が存在しなかったデータ

### 3.12 受注変更履歴【確定】

数量変更だけでなく、以下の重要変更を「受注変更履歴」として残す。

- 数量、出荷予定日、納品日、商品、出荷先、得意先、出荷区分、発送元、キャンセル 等

1件の変更履歴で扱う項目：

| 項目 | 設定方法 |
|---|---|
| 対象受注明細ID | 自動 |
| 変更日時 | 自動 |
| 変更者 | 自動 |
| 変更対象（項目） | 自動 |
| 変更前 | 自動 |
| 変更後 | 自動 |
| 増減量（数量の場合） | 自動 |
| 変更理由 | **人が入力** |
| 受付経路 | 入力（標準値の自動設定は技術設計） |
| 外部注文番号・発注番号 | 入力（ある場合） |
| 備考 | 入力（必要時） |

- 変更前後・変更日時・変更者等は極力自動記録する。人に入力させるのは原則として変更理由のみ。
- kintone標準の変更履歴だけに依存しない。業務データとして保持する。
- 具体的な実装方式（サブテーブル／別アプリ／JS自動記録等）は【未確定】（技術設計）。

> 旧前提「変更の追跡はkintoneの変更履歴等で行う」（2026-10-06）を置き換える。

### 3.13 重複受注【確定】

- 同一条件（§3.1の集約条件）の有効受注明細が既に存在する場合、自動で新規登録・自動加算しない。
- 担当者に以下を提示する。
  1. 追加発注として加算
  2. 既存受注を開く
  3. 中止
- 「追加」を選んだ場合だけ既存数量へ加算し、受注変更履歴を残す。

### 3.14 Excel / CSV取込【確定】

現状、一部得意先から1週間分のExcelを受領し、社内でkintone取込用に組み替えている。初期版では以下とする。

- 週次Excel ＝ 初回受注の一括登録
- その後の追加・減数 ＝ LINE・電話等による既存受注の変更（受注変更履歴に残る）
- 同一取込データの二重取込を警告・防止する
- 修正版Excelは例外的な訂正として扱う
- 修正版Excelの高度な自動差分反映は、初期版の必須機能ではない

具体的な取込フォーマット・二重取込の判定方式は【未確定】（技術設計）。

### 3.15 欠品と追送【確定】

- 欠品時は得意先へ連絡し、元受注の数量を当日出荷可能な数量へ修正する（受注変更履歴に残る）。
- 不足分の追送を顧客が希望した場合は、翌日以降の**別の受注明細**として登録する。
- 追送明細には `元受注明細ID` を保持する。
- 出荷側で独自に「受注10、実出荷8」のような減数を通常運用にしない。

### 3.16 苺流通システム経由の受注【確定】

- 同じ受注を、苺流通システム経由と他ルートの入力で二重登録・二重計上しない。
- 苺流通システム連携の実装方式は【未確定】（現物データの確認と技術設計）。

## 4. 予定出荷の自動生成【確定】

- **選果場出荷**の受注登録時に、出荷管理V2の**予定出荷レコード**を自動生成する。
- **産直出荷の受注明細からは、予定出荷・実出荷・在庫イベントを生成しない**。出荷済は統合受注管理V2で担当者が登録する（§3.10）。
- 該当する既存の未出荷レコードが存在すれば、自動的にそこへ紐付ける（受注明細の `出荷ID` に設定）。
- 通常の自動グルーピング条件（業務上の候補【候補】。最終的な条件は技術設計で検証する）：

> **出荷日 × 納品日 × 出荷先 × 得意先 × 発送元 × 品目**

- 品目を含める理由：なす・いちごは同じ便・送り状・出荷レコードに混載しないため【確定】。
- 得意先を含める理由：同一出荷先でも、帳合先が異なる荷物を同一送り状にまとめないため。
- この組み合わせは**一意キーにしない**。正式な識別子は `出荷ID`。
- 特殊事情では、同条件でも複数の物理発送を許容する。
- 未出荷中の受注変更は、予定出荷へ自動追従する。
- 物流業者はグルーピング条件に含めない。同一日の同一発送をヤマト・佐川に分割する通常運用はない（§6.2）。

> 旧前提「受注登録時に予定出荷を自動生成（出荷区分を問わない）、グルーピング条件は出荷日×納品日×出荷先×得意先×発送元」（2026-10-08）を置き換える。

## 5. 出荷管理V2の粒度とライフサイクル【確定】

> **1レコード = 1物理発送**

- 出荷管理V2はなす・いちご共通のアプリとする。対象は**選果場出荷だけ**。
- 1レコードは1品目だけを含む。**なす・いちごは同じ便・同じ送り状で混載せず、1つの出荷レコードにも混在させない**。同じ出荷日・同じ出荷先でも品目ごとに別の物理発送とする。
- 出荷レコードと入力画面は品目別とする。
- 出荷管理レコードは、受注登録時点から「予定出荷の器」として存在する。
- 出荷時に実績情報（個口数、送り状番号、Lot等）を加える。
- 出荷完了によって実績として確定する。

> 旧前提「1レコード = 出荷日 × 出荷先」（2026-10-04／2026-10-06、方向）を置き換える。

### 5.1 状態【確定】

- 未出荷 / 出荷完了 のみ。中間状態は持たない。

## 6. 出荷管理V2 ヘッダ項目【確定】

少なくとも以下を扱う。

| 項目 | 内容・設定方法 |
|---|---|
| 出荷ID | 正式識別子。システム自動採番 |
| 品目 | なす / いちご 等。グルーピング元の受注明細の商品から自動 |
| 出荷日 | グルーピング元の受注明細から自動 |
| 納品日 | 同上 |
| 出荷先ID / 出荷先名 | 同上 |
| 得意先ID / 得意先名 | 同上 |
| 発送元ID / 発送元名 | 同上 |
| 荷主名 | 得意先ごとの標準値から自動。例外時のみ変更（§6.1） |
| 物流業者 | 発送元×出荷先の標準値から自動。例外時のみ変更（§6.2） |
| 自動計算個口数 | 商品マスタの個口計算ルールから自動（§7） |
| 確定個口数 | 通常は自動計算値。特殊梱包時のみ手修正（§7） |
| 代表送り状番号 | 最大1件（§8.1） |
| 送り状CSV出力日時 / 出力者 | 自動記録 |
| 送り状番号登録日時 / 登録者 | 自動記録 |
| 出荷状態 | 未出荷 / 出荷完了 |
| 出荷完了日時 / 出荷完了者 | 自動記録 |
| 出荷備考 | 入力 |
| 例外完了情報 | §8.7 |
| 出荷後例外情報 | §8.8 |

### 6.1 荷主名【確定】

- 得意先ごとに標準値を持ち、自動設定する。
- 一部の得意先では、荷主名を得意先名にする必要がある。
- 例外時のみ出荷管理側で変更可能。

### 6.2 物流業者【確定】

- 発送元 × 出荷先 でほぼ決まる。標準値を自動設定する。
- 荷量の偏り等の例外時のみ変更する。
- 同一日の同一発送を、ヤマト・佐川に分割する通常運用はない。

## 7. 個口数【確定】

- 商品によって、何ケースで1個口かが異なる。
- 異なる商品でも、同じ梱包グループなら一緒に縛る場合がある。
- 商品マスタV2等に以下を持たせる。
  - 個口計算グループ
  - 標準ケース数/個口
- 例：A長1cs ＋ B品1cs、どちらも「なす通常箱」グループ（2cs/個口）→ 1個口
- 出荷管理V2には「自動計算個口数」と「確定個口数」を持つ。通常は自動値。特殊梱包時のみ手修正する。
- 端数の丸め方・複数グループ混在時の計算順序は【未確定】（技術設計で、現行の切り上げ運用を確認して決める）。

## 8. 出荷処理

### 8.1 代表送り状番号【確定】

最新の現場確認による物流業者ごとの実態：

| 物流業者 | 実態 | V2での扱い |
|---|---|---|
| ヤマト | 複数個口では、1個口ごとに異なる伝票番号が発行される。現在は最若番のみ記録している | 最若番を代表送り状番号として1件保存。全番号は管理しない。個口数が減った場合は、減った分の伝票を廃棄する |
| 佐川 | 送り状番号は1件 | 1件記録する。個口数が減る場合も、佐川側システムへ修正を入れて再発行する |
| その他便 | 伝票番号自体が存在しない場合がある | 空欄可 |

正式な表現：

> **V2では、1物理発送につき代表送り状番号を最大1件保持する。**

- ヤマト・佐川では通常入力する。ただし業務を止めない原則により、緊急時は警告＋理由記録で出荷完了を可能とする（§8.7）。
- 送り状バーコードのタブレットカメラ読取は引き続き検討する【方向】。

> 旧前提「同一出荷先で10個口でも送り状番号は1つ」（2026-10-04／2026-10-06）を置き換える。

### 8.2 送り状CSV【方向】

- 現行では、kintoneからCSVを書き出し、ヤマト・佐川・その他該当ソフトの送り状発行ソフトへインポートしている。
- V2では、送り状CSVの出力元を出荷管理V2とする。
- 物流業者ごとのCSVレイアウトは、後の技術設計・現物確認で確定する【未確定】。

### 8.3 実出荷明細【確定】

- 通常は受注明細から自動生成する。通常は 1受注明細 → 1実出荷明細。
- 受注内容と同じなら、現場は触らない。

少なくとも以下を扱う。

| 項目 | 内容 |
|---|---|
| 実出荷明細ID | 正式識別子 |
| 元受注明細ID | 生成元の受注明細 |
| 受注商品ID / 名称 | 受注明細の商品（スナップショット） |
| 実出荷商品ID / 名称 | 実際に出荷した物理商品 |
| 実出荷数量 | なすはケース、いちごはパック（数量単位は商品マスタに従う） |
| 差異区分 | 受注内容との差異の区分 |
| 差異理由 | |
| 明細備考 | |

- 在庫を減らすのは、受注商品ではなく**実出荷の物理SKU**である（在庫管理対象のSKUのみ。§8.6）。
- 差異区分の値は【未確定】（技術設計で具体化）。

### 8.4 AB混合 / BC混合【確定】

- AB混合・BC混合は販売商品として今後も販売可能。廃止商品ではない。
- 選果場の確定方針として、**物理的な混合箱は作らない**。
- 例：受注 AB混合 10cs → 実出荷 A品 6cs ＋ B品 4cs（実出荷明細2件）
- 配分比率は固定しない。その日の出来高・在庫状況で決める。
- 商品マスタ側で「許容実出荷商品」を定義する。
  - AB混合 → A品・B品のみ許容
  - BC混合 → B品・C品のみ許容
- 混合商品の分解は正常運用なので、差異理由を人に入力させない。
- 在庫を減らすのは実出荷商品（A品・B品等）。
- 混合商品の数量単位・C品kg換算等の制約は、現物SKUの確認と技術設計で扱う【未確定】。固定1対1・固定配分率は仮定しない。
- モニター初期版では、AB/BCをA/B等へ事前配分せず、「AB混合 ○cs」のまま表示する（§9）。

### 8.5 出荷Lot【確定】

- 商品ごとに「出荷Lot管理対象 / 対象外」を持つ。Lot管理対象商品のみ、Lot入力を通常要求する。
- 1実出荷明細に複数Lotを許容する。
- 既知の6桁出荷Lot（商品Lot 2桁 ＋ 日付Lot 2桁 ＋ 生産者Lot 2桁）は**なすの現行運用**である。この番号体系をいちごに一律に要求しない。
- いちごの出荷Lotの番号体系・入力方式は【未確定】（要調査）。
- 商品Lotを一意キーにしない。
- Lot別の使用数量はデータとして持つが、現場には原則入力させない。
  - 在庫の古い日付からFIFOでシステムが自動配分（提案）し、実態と異なる場合だけ修正する。
  - なすは実日付、いちごはパック詰め日をFIFOの基準とする。いちごは同じ生産者・物理SKUの在庫の中で古い順に使う（§11）。
- Lot入力UI・FIFO自動配分UIは【未確定】（技術設計）。

### 8.6 出荷完了【確定】

- 出荷完了は、原則トラック出発後（なすはLot入力後）に実行する。
- 完了操作により、以下を自動実行する。
  1. 出荷管理V2を「出荷完了」にする
  2. 実出荷明細を基準に、在庫管理V2へ出荷イベントを作成する。対象は、商品マスタ等でSF所有在庫の管理対象（選果場在庫管理対象）と判定された実出荷物理SKUだけとする（産直出荷は出荷管理V2の対象外のため、ここには現れない）
  3. 関連する統合受注管理V2の受注明細を「出荷済」に更新する
- 選果場出荷であっても、在庫管理対象とは限らない。在庫管理対象外の物理SKUだけの出荷でも、1と3は通常どおり行う。在庫イベントを作らないことは例外完了の理由にならない。
- 完了日時・完了者は自動記録する。

### 8.7 例外完了【確定】

以下のような場合も、原則として業務を止めない。

- システム在庫不足
- Lot未入力
- 代表送り状番号未入力
- 個口数未確定
- 混合商品の数量不一致
- その他情報不足

扱い：

- 警告内容はシステムが自動記録する。
- 人は例外理由を選択し、必要時のみ備考を入力する。
- 例外完了日時・実行者を自動記録する。
- 一時的に理論在庫がマイナスになっても、実際に出荷した事実の記録を優先する。
- 例外理由の選択肢は【未確定】（技術設計で具体化）。

### 8.8 出荷後の記録訂正と出荷後例外【確定】

記録誤りの訂正と、実際の出荷後の事象を区別する。

**記録誤りの訂正**

- 出荷完了後に記録の誤り（数量・SKU・Lot等）が判明した場合は、訂正できる。
- 訂正時は変更履歴・変更理由を残し、既に計上した在庫との差分調整で整合させる。
- 無履歴の直接上書き・二重出庫は禁止する。

**出荷後例外（実際の事象）**

- 顧客がキャンセル連絡を忘れており出荷後に停止依頼が来るケース等は、元の受注・出荷を取り消すのではなく、**出荷後例外として記録**する。
- 例外種別の例：配送停止 / 営業所引取 / 返送 / 別販売 / 廃棄 / その他
- 返品・再出荷も、初期版では出荷後例外として記録する。商品がSF在庫に戻り再販売可能となれば、在庫管理V2で在庫調整する。
- 専用の返品・再出荷機能、専用アプリは作らない。初期版では出荷管理V2の付帯情報で十分とする。

> 旧前提「出荷完了後の重要項目は、原則修正不可」（2026-10-08）を置き換える。

## 9. 選果場モニター【確定】

- なすといちごは**完全に別画面**とする。
- Source of Truthはどちらも統合受注管理V2（いちごは苺流通システムの選果場振り分け分を含む）。モニターは派生情報。
- 産直出荷は対象外。選果場出荷でも、商品マスタのモニター集計対象属性で対象外となる商品は対象外。

| | なす | いちご |
|---|---|---|
| 表示 | 規格別の必要**ケース数** | 販売先別・規格別の必要**パック数** |
| 集計 | 入り数違いの物理SKUでも、同じ「モニター集計規格」にまとめる | 受注数量（パック）をそのまま集計する。ケース→パック換算はしない |
| 混合 | AB/BCは初期版では混合規格名のままケース表示 | — |

- いちごの選果場製造目標は、苺流通システムのアライド向けSF選果場振り分け分＋その他販売先の選果場出荷分とする。同じ注文を二度加算しない。算出の詳細は BASIC_ARCHITECTURE.md §11。
- V2モニターはシステム移行日Tから使用する。旧受注はV2へ移さないため、モニターにも含まれない。T〜旧受注完了の間の扱いは、本番切替までに解決すべき運用上の確認事項【未確定】（BASIC_ARCHITECTURE.md §3.5）。

> 旧前提「いちごは受注数量（ケース）× 1ケース当たりパック数で換算」（2026-10-08）を置き換える。

### 10.1 商品マスタV2へ引き継ぐ属性【方向】

関連する確定事項：

- **なす物理SKU【確定】**：ケース入り数が異なるものは別の物理SKUとして登録する（例：A長80本入 / A長70本入）。受注・出荷・完成品在庫も別SKUで管理する。モニター集計規格は両方とも `A長` にできる。
  - 背景：入り数は時期により2段階。切替時期は毎年おおむね同じだが微妙に前後する。同じ出荷日でも取引先によって旧入り数／新入り数が混在し得る。
- **FLAMとの関係【確定】**：kintone物理SKUとFLAM商品（なすは価格変更により4段階）は別概念。「kintone商品1件 = FLAM商品コード1件」の単純な1対1設計は禁止。FLAM連携詳細は後工程。

## 11. 在庫管理V2との接続【確定】

在庫管理V2の詳細設計の前提として、以下が確定している。

- 在庫管理V2はなす・いちご共通の業務基盤とする。管理軸・数量単位は品目ごとに変える。
- 初期の在庫イベントは「入庫（なす仕切り確定／いちご買取確定）/ 出荷 / 在庫調整」の3つとする。
  - > 旧前提「仕切入庫 / 出荷 / 在庫調整」（2026-10-08）の「仕切入庫」を置き換える。
- 出荷イベントは、出荷管理V2の出荷完了時に実出荷明細を基準に作成する（§8.6）。対象は、商品マスタ等でSF所有在庫の管理対象と判定された物理SKUだけ。在庫予約では数量を減らさない。
- **在庫の管理軸と数量単位**：

  | 在庫区分 | 管理軸 | 数量単位 |
  |---|---|---|
  | なす完成品在庫 | 物理SKU × 実日付 × 日付Lot | ケース |
  | なす半端在庫 | 規格 × 実日付 × 日付Lot | 本数 |
  | いちごSF買取品 | 生産者 × 物理SKU × パック詰め日 | パック |
  | いちご生産者返却品 | SF所有在庫の対象外 | — |

  - 半端もFIFO対象である。規格だけで集約して日付を失わないこと。
  - 生産者番号は在庫管理軸にしない。
  - > 旧方向「A/B品は完成品も本数ベースで内部管理する」（2026-10-04）を置き換える。
  - なす半端在庫の定義は2026-10-08のまま維持する（2026-10-09 ユーザー確認）。
- **C品の在庫管理単位はケース**でよい。
  - > 旧前提「C品はkgで在庫管理する」（2026-10-04）を置き換える。
  - なす仕切り管理V2のC品の仕切り数量はkgとする（2026-10-09 確定）。換算値は物理SKUの属性に従う。
- **いちご在庫**：
  - SF買取確定品だけをSF在庫とする。パック詰め日をFIFOの基準とし、買取日とは別データとして持つ。
  - 販売先別の在庫所有・独占引当にはしない。
- **なす在庫Lot**：
  - 在庫段階では生産者番号は管理不要。必要なのは「実日付・日付Lot ＋ 物理SKU（完成品）／規格（半端）」。
  - 現場表示は「商品Lot 2桁 ＋ 日付Lot 2桁 ＝ 4桁」を使用可能。ただし4桁自体をDBの一意キーにしない。
  - 日付Lotは月を含まず翌月同日に重複するため、日付Lotだけでなく実際の暦日（実日付）を管理軸に含める。
  - 同じ管理軸（完成品：物理SKU・実日付・日付Lot／半端：規格・実日付・日付Lot）なら、生産者が異なっても在庫は合算する。
- **詰め替え・半端**：
  - 例：80本入1cs（実日付D・日付Lot L）を70本入へ詰め替え → 80本入SKU（D・L）−1cs、70本入SKU（D・L）＋1cs、半端（A長・D・L）＋10本。
  - 初期版では厳密な製造変換履歴を作らず、「在庫調整」で扱う。
  - 現場確認：選別時、半端の入った箱にはLot番号を2枚付ける場合がある。
  - 80→70本等の詰め替えで半端を組み合わせて箱を作る場合は、古い日付を採用し、現物ラベルの生産者番号は `00` とする。FIFO上の年齢をリセットしない。
  - システム内部でも、詰め替え後の在庫は元在庫のうち**最も古い実日付・日付Lot**を引き継ぐ。
- 産直出荷は選果場在庫の対象外（維持）。
- **正式在庫管理開始日S**：
  - システム移行日Tとは別の管理上の開始日とする。旧アプリの未出荷受注がすべて完了し、実棚卸・補正を行う時点で設定する（S ≧ T。TとSが異なる暦日であることは要件としない）。T〜S前のV2在庫は暫定値。
  - Sでの棚卸・補正は、商品別の総数量ではなく、**確定済みの在庫管理軸ごとに正しい残高を登録する**ことを原則とする。
    - なす完成品：物理SKU × 実日付 × 日付Lot
    - なす半端：規格 × 実日付 × 日付Lot（FIFO）
    - いちごSF買取品：生産者 × 物理SKU × パック詰め日
  - 初期残高・差分調整は履歴付きで登録する。

|---|---|---|
